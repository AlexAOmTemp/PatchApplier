# MCPBridge — unified toolkit

Обзор проекта и навигация по документам. +

> **Статус:** обзор и навигация. Точные сигнатуры — в `CODE_INDEX.md`. Принципы — в `ARCHITECTURE.md` и `DECISIONS.md`. Для работы LLM — `LLM_START.{lang}.md`. Если документ расходится с кодом — верь коду.
>
> **Раскладка проекта.** Всё, что генерирует утилита (индексы, `.version`, `.manifest.json`, `.index_meta.json`, рантайм MCP `patch.json` / `outputs.json` / `bridge_log.jsonl`), живёт в служебном каталоге проекта — по умолчанию `<project>/.patch_applier/` (`state_dir` в конфиге). `tools_schema.json` — исключение: он toolkit-global, лежит в `<toolkit_root>/runtime/state/`. Сама утилита может быть в любом месте, не обязательно внутри проекта.

## Что это

<!-- summary: Один фреймворк, четыре источника (docs / Python / Luau-код в MCP или Rojo / Roblox-сцена), один формат патчей. -->
<!-- tags: overview, purpose -->

Унифицированный toolkit для правки проекта через LLM-патчи. Один каркас, **четыре источника**:

- **Markdown-доки** — `FilesystemBackend`, секции.
- **Python-код** — `FilesystemBackend`, символы через AST.
- **Luau-код** — два режима: **MCP** (`.Source` в Studio, dot-notation путей) или **Rojo** (файлы на диске, обычные пути, AST-парсер).
- **Roblox-сцена** (Parts, GUI, Folders) — всегда через `MCPBackend` (subprocess `bridge.py` ↔ Roblox Studio), независимо от режима Luau-кода.

Цель: единый формат патчей и ответа (`Result` + diff) поверх любых источников; адресация по структурным единицам (секция, символ, statement) вместо построчных правок; экономия контекста LLM.

## Зачем

<!-- summary: Три изначальные проблемы: разные утилиты, баги моста, navigation overhead. -->
<!-- tags: motivation, problems -->

1. **Доки и код жили в разных утилитах** — разный формат патчей, разный ответ, разный GUI. Сейчас — один toolkit, один `TOOL_MAP`, один `##RESULT:`.
2. **MCP-мост имеет известные баги** (`multi_edit` отчитывается `applied`, но не пишет) — лечатся в `MCPBackend` через retry, verify-after-write, control-char guard.
3. **Контекст LLM уходил на navigation** — 5–10 вызовов на рефактор. Решается символьными тулами: `read_symbol`, `replace_symbol_body`, `insert_symbol`.

## Правила работы с Roblox-модом

<!-- summary: Открытая вкладка Studio — риск потери правок LLM; порядок работы с Roblox-модулями. -->
<!-- tags: roblox, ux, editor-buffer -->

Когда LLM правит **Roblox-модули** (`ReplicatedStorage.X`, `ServerScriptService.Y`), утилита пишет в `.Source` инстанса. Это работает корректно во всех случаях, кроме одного:

**Открытая вкладка Studio — источник конфликта.** Если модуль открыт в редакторе Studio, редактор держит собственный буфер. Правки LLM идут в `.Source` и в буфер **не подхватываются автоматически**. Если потом закрыть вкладку (Studio сохраняет буфер при закрытии) или сохранить `Ctrl+S` — буфер затирает `.Source`, и все правки LLM **пропадают**. Verify-after-write этого не ловит: проверка идёт в момент записи, а конфликт возникает позже, при сохранении из Studio.

**Порядок работы:**

1. **Перед правкой Roblox-модулей закройте их вкладки** в Studio. Проще всего — держать открытым только то, что смотрите сейчас, и закрывать вкладки перед тем, как просить LLM править модуль.
2. **После правки LLM**, если вкладка всё же была открыта — **переоткройте её** (закрыть + открыть заново), чтобы подхватить актуальный `.Source`.
3. **Не сохраняйте в Studio** буфер модуля, который параллельно правит LLM. Либо сохраните свою работу **до** сессии правок, либо после — но не в середине.
4. Если вы правили модуль в Studio и хотите, чтобы LLM продолжил — сначала `Ctrl+S`, потом уже патч.

**Признак, что конфликт уже произошёл:** `read_file` показывает версию, отличную от того, что вы видите в редакторе Studio. Переоткройте вкладку — расхождение уйдёт. Если после переоткрытия редактор показывает **старую** версию (без правок LLM) — значит, Studio закоммитила свой буфер и затёрла `.Source`.


## Перезапуск GUI после правок кода утилиты

<!-- summary: Правки .py утилиты не подхватываются на лету — Python кэширует импорты в памяти процесса; после изменения кода нужен перезапуск GUI. -->
<!-- tags: gui, troubleshooting, development -->

GUI-процесс держит модули утилиты (`tools/*.py`, `indexers/*.py`, `backends/*.py`, ...) в памяти с момента импорта. **Правки кода на диске не подхватываются на лету** — новый вызов тула исполнит старый байткод.

**Симптом.** После правки тула его поведение не меняется; падает с ошибкой, которой в исходнике уже нет; `rebuild_*` показывает дифф «без изменений», хотя файл на диске изменился (старый загрузчик пересобирает из старых данных).

**Лечение.** После любой правки `.py` утилиты — **перезапустите GUI**. CLI и `run_python` всегда стартуют свежим процессом, там проблемы нет.

**Проверка.** Если подозреваете, что работает старый код — откройте файл (`read_file`) и убедитесь, что исходник правильный. Если да, а поведение — нет, перезапуск GUI обязателен.
