## 1. Workflow, для которого всё строится
<!-- summary: Юзер-чайник даёт папку RimWorld и задачу «сделай мод». LLM исследует незнакомое дерево 30k файлов: обзор → гипотеза → проверка → сужение. Работает только если исследование персистентно. -->

### 1.1 Сценарий

Юзер не разбирается в программировании и файлах. Он умеет одно: указать проекту папку. Всё остальное — не его. Он открывает утилиту, указывает `C:\RimWorld\` (или любую другую корневую папку игры), и пишет LLM:

> «Сделай мне мод, который чинит крафт блоков.»

Что происходит дальше — центральный сценарий. LLM никогда раньше не видела этот проект. Она знает про RimWorld в общем (жанр, формат модов, структура XML, Harmony-патчи), но не знает конкретно, где в этом дереве лежит то, что нужно чинить.

### 1.2 Что делает LLM

Исследование. Итерации, не одна:

1. **Обзор.** Посмотреть форму дерева. `survey_dir("")` — 30 043 файла, 86 подкаталогов-модов, `Source/` с исходниками, `Mods/` с чужими модами.
2. **Гипотеза.** «Пользовательский мод будет где-то в `Mods/`, но его ещё нет. Мне надо понять, какой мод добавить, и как выглядит целевой файл-пример в существующих модах.»
3. **Проверка.** Открыть один-два чужих мода, посмотреть структуру `Defs/`, `Patches/`, `About/`. Понять конвенцию.
4. **Сужение.** «Мне не нужны `Source/` (это движок), `Mods/0000000001`…`Mods/0000000085` (не наш мод, мы создаём новый). Оставить только место, куда писать, и один пример.
5. **Работа.** Собственно правка: создать файлы, написать XML.

Это **stateful discovery**: цель становится известной в процессе, не в начале. Пункт 5 неотделим от пунктов 1–4.

### 1.3 Что мешает сегодня

Каждая итерация начинается заново. Инструменты дают **снимок** дерева, но не **память исследования**:

- После шага 4 LLM знает: «`Source/` — просмотрен, пусто. `Mods/0000000001..85` — не наш мод. Оставить `Mods/1201382956` и `Source/Building`». Куда это записать? **Никуда.**
- На шаге 5 LLM делает `grep` — и без явного `directory=` получает 30 043 пути. Снова. Каждый вызов.
- Новая сессия (через час, после обрыва контекста) — **ничего не помнит**. Начинает с `survey_dir("")`. Снова.
- Если пользователь дважды откроет окно через час, чтобы закончить — LLM потратит первые 10 вызовов на то, что уже было решено в первой сессии.

Проблема не в том, что индекс большой. Проблема в том, что **решения об исключении негде хранить**.

## 2. Почему существующие механизмы не подходят
<!-- summary: Разбор .patchignore, индекса, структурных тулов, directory=, survey_dir — каждый не решает discovery. -->

| Механизм | Почему не то |
|---|---|
| `.patchignore` | Пишет **человек**, это security-граница («не показывай `__pycache__` никогда»). LLM её не трогает. Если LLM через неё начнёт исключать просмотренное — она сломает пользовательские правила. |
| Индекс (`INDEX.md`, `CODE_INDEX.md`) | File-level. На 30k файлов — 30k строк. Полезен, когда **знаешь, что искать** (`find_symbol`, `grep`). Для discovery — шум. |
| Структурные тулы (`read_unit`, `replace_unit`) | Для **правки**, не для поиска. Требуют точного адреса, которого у LLM в начале нет. |
| `subtree=` (идея-конкурент) | Для **известной цели**. Сужает индекс до подкаталога. Не помогает, когда цель — «где-то в этих 30k файлах». |
| `directory=` в каждом вызове | Требует дисциплины. Забыла один раз — получила 30k путей. |
| `survey_dir` | Снимок. Не помнит прошлых решений. |
| `run_python` / скрипты | Может обойти дерево и решить, но результат — в stdout, не в персистентной памяти. И требует `exec.enabled`, который по дефолту выключен. |

Ничто из этого не даёт **память** — место, куда LLM пишет «`/Source` просмотрен, пусто» и где следующая сессия это увидит.

## 3. Что нужно от механизма
<!-- summary: Семь свойств — персистентность, монотонность, обоснование, append, автоматическое уважение, директорный уровень, re-inclusion. -->

Механизм должен уметь:

1. **Переживать сессию.** Сохраняться на диск. Переживать рестарт GUI, обрыв контекста, закрытие и открытие через день.
2. **Накапливаться монотонно.** LLM исключает по 5–10 каталогов за итерацию, не переписывает всё каждый раз.
3. **Хранить обоснование.** «`/Source` просмотрен, пусто» — не комментарий для человека, а часть решения. Следующая сессия читает и понимает, *почему* `/Source` не в работе, а не только *что* он не в работе.
4. **Принимать добавления, не только замены.** `add`, не `set`. `set` — редкий случай «начать заново».
5. **Уважаться автоматически.** Если LLM исключила `/Source`, тулы не должны показывать файлы оттуда. Без `respect_scope=True` в каждом вызове — это должно быть по умолчанию для read-тулов.
6. **Показывать директорный уровень.** Когда LLM смотрит «где я сейчас», ей нужны не 142 файла, а 5 подкаталогов со счётчиками и статусами.
7. **Позволять передумать.** Если LLM исключила `/src`, а потом решила заглянуть — должно быть `!/src`, не полный сброс.

## 4. Предложение — `.llmscope` как память исследования
<!-- summary: Формат файла, exclude-семантика (не include-only), комментарии-статусы, negation. -->

### 4.1 Семантика — exclude-mode, не include-only

Файл `.llmscope` живёт в `state_dir`. Синтаксис — как `.patchignore`. **Семантика — обратная.**

`.patchignore`:
```
.*              # исключить всё, что матчится
!__pycache__    # кроме — re-inclusion
```

`.llmscope` — то же самое, но по умолчанию «видно всё»:
```
# пустой файл = видно всё

# перечисленное исключается
/Source         # это движок, не наш мод
/Mods/*         # все моды кроме целевого
!/Mods/1201382956   # наш мод, оставить
```

**Почему exclude-mode, а не include-only (как в §2.2 DECISIONS).**

В §2.2 файл описан как «include-only белый список: пустой = видно всё; непустой = показывай только то, что подходит под паттерны». Тогда `/core # просмотрен` в файле означает **«видно только /core»** — прямо противоположное намерению.

Пример из обсуждения:
```
/core   # просмотрен, не содержит нужных файлов
/src    # пока не просматривался, временно исключён
```
Здесь `/core` и `/src` — **исключены**. Это exclude-семантика.

В exclude-mode исследование идёт **постепенно**: за итерацию добавить 5–10 исключений, а не переписать файл целиком, сужая с 30k до 142. Монотонность (требование 2) ложится естественно: `add_scope` аппендит строки, ничего не переписывая.

### 4.2 Комментарии — first-class статусы

Комментарий в `.llmscope` — **не для человека**. Это запись решения. LLM пишет:

```
# Просмотрен, пусто
/Source

# Не наш мод
/Mods/0000000001
/Mods/0000000002
...

# Артефакты сборки, никогда
/Mods/1201382956/Assemblies

# Целевой мод — оставить
!/Mods/1201382956
```

Три типа комментариев, соответствующие трём статусам в голове LLM:

- **«просмотрен, пусто»** — исключён, потому что проверила.
- **«не наш X»** — исключён по признаку (по номеру, по имени, по дате).
- **«артефакты / never»** — исключён по типу содержимого.

Соглашение о формулировках — **свободное**. Инструмент не парсит `# просмотрен` как формальный токен; он просто показывает комментарий рядом с паттерном в выводе `survey_dir` и `get_status`. Формализация — открытый вопрос (§7.2).

### 4.3 Формат и правила

- Один glob на строку. `#` — комментарий. Пустые строки игнорируются (но сохраняются в файле как разделители).
- **`!pattern`** — re-inclusion. Как в `.patchignore`. Порядок важен: последнее правило выигрывает.
- Паттерны — сегментные, как в `.patchignore`. `*` не пересекает `/`. `/Source` матчит сегмент, `Source/*` — подкаталоги внутри.
- **Root-relative с basename**, как везде в FS-тулах: `/Source`, `/Mods/1201382956`.
- Пустой или отсутствующий файл — «видно всё».

### 4.4 Не security-boundary

Как в §2.2: scope — не песочница. LLM может расширить себе scope одним `clear_scope()`. Это не дыра, потому что scope — область видимости, а не право доступа. Пользователь видит `## Scope` в `get_status` и может поправить. Подтверждение не требуется.

## 5. Точки интеграции
<!-- summary: Тулы (get/add/set/clear), survey_dir под scope, индексаторы по scope, get_status dashboard. -->

### 5.1 Тулы

Четыре, а не три:

| Тул | op | Что делает |
|---|---|---|
| `get_scope` | read | Текущее содержимое `.llmscope` — текст как есть + разбор (какие пути исключены, какие комментарии к ним). |
| `add_scope` | write | Добавить строки (аппенд). Основной тул исследования. |
| `set_scope` | write | Заменить целиком. Редко — «начать заново». |
| `clear_scope` | write | Очистить. Эквивалент «видно всё». |

Отличие от §2.2: **`add_scope` добавлен как основной тул**, не опциональный. Исследование монотонно, и это должно быть выражено в API, а не в инструкции «не забывай переписывать файл целиком».

`get_scope` возвращает **не только текст**, но и структуру: список исключённых путей + комментарии. Это для того, чтобы LLM в новой сессии могла прочитать состояние как данные, а не парсить свой же файл.

### 5.2 `survey_dir` под scope

Сейчас `survey_dir` игнорирует scope. Должен уважать и показывать обе стороны:

```
survey_dir("")

> RimWorld: 30043 files (filtered by .llmscope)
> In scope:  142 files
> Excluded:  29901 files
>
> In scope — top subdirs:
>   Mods/1201382956           142   [.xml:112  .lua:8  .md:22]
>
> Excluded — by comment:
>   # Просмотрен, пусто
>   /Source                 12043
>   # Не наш мод
>   /Mods/0000000001..85    17032
>   # Артефакты сборки
>   /Mods/1201382956/Assemblies    826
```

Вот это — **карта поискового пространства**. LLM смотрит и видит: «осталось 142 в целевом моде, всё остальное под комментариями». Следующая сессия читает то же самое и понимает, где она.

Сейчас ни `survey_dir`, ни `get_index` этого не дают.

### 5.3 Индексаторы

`rebuild_index` / `rebuild_code_index` / `rebuild_lua_code_index` собирают **только то, что в scope**. Индекс реально маленький: 142 файла, а не 30 043.

Инкрементальность: при сужении scope (LLM добавила исключения) индекс **пересобирается**. Но пересборка — это быстро, потому что файлов в scope мало. Полная пересборка 142 файлов дешевле инкремента 30 043.

При расширении (`!pattern` или `clear_scope`) — то же самое: пересборка по новому scope. Не инкрементально, но быстро, потому что обычно расширяется на один каталог, не до всего.

Открытый вопрос — что делать с **файлами вне scope в diff**. Вариантов два:
- Diff показывает только изменения в scope. Если LLM через `respect_scope=False` читала файл вне scope и что-то поменяла — изменения не покажутся.
- Diff показывает всё, но `get_index` фильтрует.

Первое проще и согласовано с «scope — единственная область работы». Второе честнее — «если что-то поменялось, покажем». См. §7.4.

### 5.4 `get_status`

Секция `## Scope` — **dashboard**, не «вот файл». Показывается **всегда при непустом `.llmscope`**, независимо от `sections=` (как в §2.2).

```
## Scope
Working set: 142 files (Mods/1201382956)

# Просмотрен, пусто
/Source

# Не наш мод
/Mods/0000000001..85

# Артефакты сборки, никогда
/Mods/1201382956/Assemblies

# Целевой мод
!/Mods/1201382956
```

Формат: заголовок с рабочей областью + комментарии и паттерны как в файле. Не «вот содержимое файла», а «вот где ты и что уже знаешь».

## 7. Открытые вопросы
<!-- summary: Пять — формализация статусов, директорный индекс, diff вне scope, миграция, смена корней. -->

### 7.1 Что показывать в `INDEX.md` под scope

Два варианта:

- **File-level** — как сейчас, только меньше файлов (56 вместо 30k). Привычно, работает с существующей логикой `parse_index_text` / `diff_index`.
- **Directory-level** — новая структура: «папка → файлы с секциями». Компактнее, но требует переписать renderer и diff.

Пока — file-level. Directory-level — если file-level окажется всё ещё слишком крупным на 1000+ файлов в scope.

### 7.2 Формализация статусов

Свободный текст комментария vs формальные токены типа `# status: explored`.

**Свободный текст:** LLM пишет естественно, ничего не ломается при переформулировке. Но инструмент не может сгруппировать комментарии в `survey_dir` по типу (все «просмотрено» вместе, все «никогда» вместе).

**Формальные токены:** группировка работает, но добавляет ригидности. LLM должна помнить синтаксис.

Промежуточный вариант — **набор ключевых слов** (`explored`, `skip`, `later`, `target`), которые инструмент распознаёт и подсвечивает, но строго не требует. Как сейчас у маркеров индекса: `⚠ large`, `◉` — это факты, но не обязательный язык.

Решить при первом реальном использовании. Пока — свободный текст.

### 7.3 Поведение при смене корней

Как в §2.2: **тихо игнорировать**. Scope может ссылаться на удалённый корень, паттерн просто не матчится. Когда корень вернётся — снова начнёт работать.

Для `.llmscope` это особенно важно: пользователь-чайник может указывать проект «не туда», потом «перетуда». Scope не должен разваливаться.

### 7.4 Diff вне scope

Если LLM через `respect_scope=False` что-то поменяла вне scope — показывать это в diff'е или нет?

Аргументы за «не показывать»: scope — единственная область работы, изменения вне — «не должно было случиться». Аргументы за «показывать»: изменение есть изменение, LLM должна видеть последствия своих действий.

Скорее «показывать»: раз LLM осознанно сняла `respect_scope` и поменяла — она знает, что делает, и не хочет сюрпризов. Решить на первой реализации.

### 7.5 Миграция

Когда механизм появится — `.llmscope` отсутствует, это норма. Пустой/отсутствующий = видно всё. Старые сессии не ломаются.

Обратный случай: пользователь удаляет `.llmscope` вручную. Поведение — то же, «видно всё». Scope теряется, но GUI об этом не кричит.

## 8. Отношение к §2.2 DECISIONS.md
<!-- summary: Что берём без изменений, что меняем, что добавляем. -->

### Берём

- **Персистентный файл в `state_dir`**, не поле в config. Причина та же: переживает рестарт, LLM может менять, пользователь — тоже.
- **Комментарии — first-class.** Живут, читаются, объясняют.
- **Не security-boundary.** LLM может снять, пользователь увидит.
- **Тихое игнорирование** при смене корней.
- **Секция `## Scope` в `get_status`** показывается всегда при непустом файле.
- **Path-форма** — root-relative с basename.
- **Синтаксис** — как `.patchignore` (glob-строки, `#`, `!`).

### Меняем

- **Семантика — exclude-mode, не include-only.** Аргументация в §4.1. Include-only противоречит примеру использования.
- **`add_scope` — основной тул**, не опциональный. Исследование монотонно.
- **`survey_dir` под scope** показывает обе стороны (in scope + excluded + комментарии). Сейчас этого нет ни в дизайне, ни в коде.
- **`get_status ## Scope` — dashboard**, не «покажи файл». Формат: working set + комментарии + паттерны.

### Добавляем

- **Re-inclusion через `!`** — если LLM передумала. У `.patchignore` уже есть, симметрия бесплатна.
- **Разбор в `get_scope`** — не только текст, но структура (пути + комментарии).

## 9. План реализации
<!-- summary: Порядок шагов, если решено делать. Начать с parse+read, не с тулов. -->

Если решено реализовать, порядок такой:

1. **`toolkit/config/llmscope.py`** — `parse` / `read` / `write` / `matches` по аналогии с `patchignore.py`. Плюс `add_lines` для `add_scope`. Тесты — на парсер и матчер, как для `patchignore`.
2. **`toolkit/tools/scope.py`** — четыре тула: `get_scope`, `add_scope`, `set_scope`, `clear_scope`.
3. **Секция `## Scope` в `tools/status.py`** — рендер dashboard'а.
4. **`survey_dir` respect scope** — расширить `SurveyDirTool.execute` двумя ветками (in scope, excluded).
5. **`respect_scope=True`** в read-тулах — `read_file`, `read_unit`, `list_files`, `grep`, `grep_replace`, `grep_replace_mcp`.
6. **Индексаторы под scope** — фильтр на входе `backend.list()`. Не переписывать walk-логику, отфильтровать на этапе получения путей.
7. **LLM_START §7 (ru + en)** — четыре тула.
8. **DECISIONS.md §2.2** — обновить после реализации: заменить include-only на exclude-mode, добавить `add_scope`.

Порядок важен: начать с парсера и матчера, потому что от них зависит всё остальное. Тулы — после того как парсер работает. `survey_dir` — до индексаторов, потому что он проще и сразу даст обратную связь, работает ли scope как задумано.

## 10. Метрика готовности
<!-- summary: Как понять, что механизм нужен, и что он работает. -->

**Когда делать.** В §2.2 метрика такая: «сколько раз за сессию LLM была бы рада записке себе? Если 3+ — делаем». Метрика хорошая, но в новом свете её надо переформулировать:

> **Сколько раз за сессию LLM повторяет уже сделанное исследование?**

Если сессия в RimWorld-подобном проекте тратит первые 5–10 вызовов на `survey_dir` + `read_file` по каталогам, которые уже смотрела, — механизм нужен.

**Когда механизм работает.**

1. Новая сессия на том же проекте **не повторяет** `survey_dir("")` — `get_status` сразу показывает рабочую область.
2. `grep` без `directory=` в большом корне **не возвращает** 30k путей — возвращает только то, что в scope.
3. `rebuild_index` после сужения собирает 56 файлов **быстро**, а не 30k медленно.
4. Пользователь в GUI видит в статусе «работаю в Mods/1201382956, исключено 29k файлов» и понимает, что происходит, **не открывая файл**.

Пункт 4 — для чайника важнее, чем все остальные. Если он не понимает, почему LLM не видит весь проект, — он думает, что утилита сломалась.
