# Workspace — модель проекта в Patch Applier

<!-- summary: Workspace = один или несколько FS-roots (юзерских каталогов, без вложенности) + policy (read / write / 3 index flags) + state вне юзерских каталогов. Root идентифицируется basename'ом каталога; одноимённых нет. MCP — не root, своя нотация. Один workspace активен за раз. -->
<!-- tags: workspace, design, architecture -->

## 1. Зачем

<!-- summary: Три проблемы текущей модели: шум в юзерском каталоге, один корень, неясно что в git. -->

Сейчас «проект» в утилите = одна пользовательская директория. Из этого следует три неудобства:

- **Шум в юзерском каталоге.** Индексы, `*.manifest.json`, `*.version`, `.index_meta.json`, `runtime/` и `config.json` живут внутри проекта. Пользователь, который просто хотел править файлы, получает полтора десятка служебных артефактов рядом со своим кодом.
- **Один корень.** Нельзя собрать в один проект три разрозненных каталога: доки в `D:/docs/`, код в `D:/src/`, игра в `D:/game/`. Каждый — отдельный «проект», между ними нет общей карты.
- **Неясно, что в git.** `.patchignore` — конфиг, коммитить. `INDEX.md` — производное, не коммитить. Но и то и другое сейчас рядом, в `<project>/.patch_applier/`.

Workspace решает все три: **много roots, state снаружи, единая карта**.

## 2. Термины

<!-- summary: Workspace = roots + policy + state. Root — это FS-каталог; идентифицируется basename'ом. Никаких отдельных имён / id / label. -->

**Workspace** — единица работы. Пользователь создаёт его один раз и открывает по имени. Содержит:

- **roots** — список FS-каталогов. Минимум один. MCP — не root, у него своя нотация (см. §3).
- **policy** — правила доступа и индексации по root'ам (см. §6).
- **format / exec / mcp** — как сейчас.
- **state** — производные файлы (индексы, meta, runtime).

**Root** — один FS-каталог. У него есть:

- **path** — абсолютный путь на диске. Всё.
- **include / exclude** — глобы внутри root'а (опционально).

**Идентификация root'а — по basename его каталога.** Если пользователь добавил `D:/a/toolkit/`, root называется `toolkit`; в путях патчей он идёт как `toolkit/...`. Если добавил `D:/b/`, root называется `b`; его дерево показывает всё, что лежит внутри, включая вложенный `toolkit`, и путь к файлу — `b/toolkit/...`.

**Никаких отдельных имён, id, label, display_name.** Root — это и есть его дерево. Имя дерева — имя корневого каталога. Отображение в UI = то же имя.

**Одноимённых roots не бывает.**

**Регистр basename — case-insensitive.** `D:/Docs` и `D:/docs` — коллизия, даже на Linux. Проект, скопированный с одной ФС на другую, не должен ломаться от смены регистра. Сравнение basename'ов — приведением к нижнему регистру. Два root'а с basename `toolkit` — ошибка при добавлении (см. §8). Пользователь либо выбирает другой каталог, либо расширяет один из root'ов вверх по дереву так, чтобы basename'ы различались.

**State** — каталог с производными файлами. По умолчанию — `<toolkit_root>/runtime/workspaces/<id>/`. В embedded-режиме — указатель на любой путь, который пользователь выбрал (например, внутри своего проекта).

**Один workspace активен за раз.** Параллельные сессии не поддерживаются — если нужно, пользователь запускает несколько копий GUI.

## 3. Адресация

<!-- summary: Путь в патче = <basename-root>/<rel-path>. Basename уникален (одноимённых root'ов нет). Абсолютный путь — escape hatch. MCP — не root, без префикса. -->

**Путь в патче = `<basename-root>/<rel-path>`.**

`basename-root` — имя корневого каталога root'а. Уникально внутри workspace по построению: одноимённые root'ы запрещены.

Примеры:

- root `D:/docs/` → basename `docs`. Путь: `docs/REQUIREMENTS.md`.
- root `D:/src/` → basename `src`. Путь: `src/toolkit/core/patcher.py`.
- root `D:/game/` → basename `game`. Путь: `game/ServerScriptService/Foo/init.luau`.

**Две копии одного каталога — различимы через расширение root'а вверх.** Пользователь хочет держать `D:/project1/toolkit/` и `D:/project2/toolkit/` одновременно. Варианты:

- **Вариант 1.** Добавить `D:/project1/toolkit/` (root `toolkit`) и `D:/project2/` (root `project2`). Пути: `toolkit/core/patcher.py` и `project2/toolkit/core/patcher.py`.
- **Вариант 2.** Добавить `D:/project1/` (root `project1`) и `D:/project2/` (root `project2`). Пути: `project1/toolkit/core/patcher.py` и `project2/toolkit/core/patcher.py`. Симметрично.

Что **нельзя**: добавить оба как `D:/project1/toolkit/` и `D:/project2/toolkit/` — оба получили бы basename `toolkit`, и утилита отказывает (см. §8). Пользователь сам решает, как расширить root'ы вверх, чтобы имена разошлись.

**Абсолютный путь — escape hatch.** Принимается как есть, резолвится в (root, rel-path) или отбрасывается с `sandbox`. Не рекомендуется для повседневной работы из-за длины, но валиден.

**MCP — не root.** DataModel у Roblox один на сессию Studio, у него нет каталогов и нет basename'а. MCP-путь остаётся как сейчас: `ReplicatedStorage.Shared.Modules.LuckFormula`, `ServerScriptService.Server.Services.DamageService`. Префикс не добавляется, нотация не меняется. У MCP своя нотация, у FS своя — это нормально.

**Коллизия basename с именем сервиса.** Валидация запрещает basename'ы, равные именам Roblox-сервисов (`ReplicatedStorage`, `ServerScriptService`, `Workspace`, ...) — список в `core.paths.ROBLOX_SERVICES`. Чтобы FS-путь и MCP-путь не выглядели как один.

**Что это ломает.** Существующие патчи используют пути без префикса. Миграция — см. §9.

## 4. Roots и вложенность

<!-- summary: Вложенные roots не поддерживаются. Конфликтующие политики решаются одним широким root'ом + флагами индексации. -->

**Вложенные roots не поддерживаются.**

**Workspace с нулём корней валиден.** Только что созданный workspace (до «Add root») — не ошибка. Штатный режим для чистого MCP: DataModel работает, FS-корней нет. `list("")` возвращает `[]`. Два root'а, один внутри другого (`D:/game/` и `D:/game/src/`), не разрешены. Валидация выдаёт ошибку при добавлении.

**Почему.** Вложенность создаёт конфликтующие политики: если `game` говорит `write: false`, а `src` внутри — `write: true`, неясно, какое правило важнее. Решать это через most-specific-wins можно, но это усложняет модель без реальной необходимости. Пользователь всегда может сделать один широкий root и настроить флаги индексации (см. §6), чтобы выборочно не индексировать вложенное.

## 5. Домены и индексы

<!-- summary: Три индекса (docs / code / lua) на workspace. Собираются со всех root'ов, отфильтрованных по флагам policy. Путь в индексе = <basename>/<rel>. -->

**Один индекс на домен на workspace.** Не на root. Три домена — `docs`, `code`, `lua` — и три индекса (`INDEX.md`, `CODE_INDEX.md`, `CODE_INDEX_LUA.md`). Индексы собираются со **всех root'ов workspace**, отфильтрованных по флагам policy (см. §6).

**Путь в индексе — `<basename-root>/<rel-path>`.** Один индекс показывает карту по всем root'ам сразу.

| индекс | что попадает | флаг policy |
|---|---|---|
| `INDEX.md` (docs) | `.md` файлы | `index_docs` |
| `CODE_INDEX.md` (code) | `.py` файлы | `index_py` |
| `CODE_INDEX_LUA.md` (lua) | `.lua` / `.luau` (Rojo) или DataModel (MCP) | `index_lua` |

Root, у которого все три флага `false`, не индексируется, но файлы видны для read/write (если `read: true`). Root с одним `true` — индексируется только в этот индекс.

**Include / exclude глобы** — опционально, сужают область внутри root'а: `include: ["docs/**/*.md"]`, `exclude: ["**/_build/**"]`. Дефолт — без ограничений (кроме домена и `.patchignore` / `.mcpignore`).

**Rebuild-триггер.** Успешный write → пересборка индекса того домена, к которому относится путь. Домен пути определяется по расширению: `.md` → docs, `.py` → code, `.lua` / `.luau` → lua. MCP-пути триггерят lua.

**Файлы вне index не теряются.** Если root не индексируется, файлы всё равно доступны через `read_file` / `grep` / unit-тулы по обычному пути `<basename>/...`.

## 6. Policy

<!-- summary: Policy привязана к root'ам. Пять независимых флагов: read, write, index_docs, index_py, index_lua. Ключи — basename'ы root'ов (уникальны). -->

**Policy привязана к root'ам.** Никакой cross-cutting агрегации. Вложенные roots запрещены (см. §4), значит конфликтов не бывает. Ключи — basename'ы root'ов; так как одноимённых root'ов не бывает, ключи уникальны.

**Форма данных:**

```json
{
  "roots": {
    "src":     { "read": true, "write": true,  "index_docs": false, "index_py": true,  "index_lua": false },
    "docs":    { "read": true, "write": true,  "index_docs": true,  "index_py": false, "index_lua": false },
    "project2": { "read": true, "write": false, "index_docs": false, "index_py": false, "index_lua": true  }
  }
}
```

**Пять флагов:** `read`, `write`, `index_docs`, `index_py`, `index_lua`. Все независимы.`read` и `index_*` независимы — смешивать не нужно. Возможна конфигурация `read: false, index_py: true`: файлы не видны LLM, но попадают в индекс (карта «что где лежит» без доступа к содержимому). Обратное — `read: true, index_py: false` — тоже легально (файл читаем, но не индексируется). `read: true, write: false` — можно читать, нельзя писать. `index_py: false` — Python-файлы в этом root'е не попадают в `CODE_INDEX.md`.

**Дефолт** при добавлении root'а — все пять `true`. Пользователь сужает по необходимости.

**Файл, не индексируемый ни одним флагом,** всё равно доступен для read/write, если `read: true`. Индексация ортогональна доступу.

**Что не политика.** `.patchignore` / `.mcpignore` — фильтр видимости, не policy. Они решают, что вообще попадает в карту мира; policy — что с этим можно делать. Разные слои, разные файлы.

**MCP не подчиняется policy.** Roblox DataModel не фильтруется — это уже так, остаётся так. Policy описывает только FS-roots; для MCP ничего не пишется и не проверяется.

## 7. State: external vs embedded

<!-- summary: State — каталог с workspace.json, индексами, .patchignore/.mcpignore, runtime. По умолчанию external (<toolkit_root>/runtime/workspaces/<id>). Embedded — пользователь кладёт куда хочет. Никакого реестра, только recent.json. -->
**Один каталог — весь проект.** Пользователь выбирает каталог при создании проекта. Туда утилита кладёт всё, что ей нужно. Никаких external / embedded, никаких «по умолчанию там, можно сюда». Один алгоритм: выбрал папку — там всё.

Содержимое папки проекта:

```
<project>/
  workspace.json          метаданные (roots, policy, format, exec, mcp)
  .patchignore            правила видимости FS
  .mcpignore              правила видимости MCP
  INDEX.md                производное (docs)
  CODE_INDEX.md           производное (Python)
  CODE_INDEX_LUA.md       производное (Luau)
  *.manifest.json
  *.version
  .index_meta.json
  runtime/                логи, metrics, bridge state
```

**Имя проекта** — поле `name` в `workspace.json`. Не привязано к имени каталога, пользователь задаёт при создании.

**ID проекта** — стабильный идентификатор внутри `workspace.json`. UUID или короткий hash. На адресацию и отображение не влияет; нужен для внутренних нужд (стабильная сортировка в `recent.json` при совпадающих именах).

**`recent.json` — список путей к папкам проектов.** Единственное место, где утилита помнит «последнее». Хранит абсолютные пути. При старте: верхний путь → читаем `<path>/workspace.json`. Если папки нет или файл битый — запись выкидывается, GUI открывается без проекта.

**Доступ к файлам проекта.** `workspace.json`, `.patchignore`, `.mcpignore`, индексы, `runtime/` — всегда RW для внутренних тулов и **никогда не индексируются**. LLM читает индексы через `get_index`, политики — через `get_status`. Прямой доступ возможен, но не требуется.

**Если папка проекта физически внутри одного из корней** (пользователь положил её в `D:/my-game/.patchapplier/`, а `D:/my-game` — root) — это допустимо. Файлы проекта всё равно не участвуют в индекс-обходе корня (правило «никогда не индексируются»). Конфликтов нет.

**Перенос проекта.** Пользователь может скопировать или переместить папку проекта куда угодно. Roots внутри `workspace.json` — абсолютные пути, к расположению самой папки проекта не привязаны. При следующем открытии через GUI — путь обновляется в `recent.json`.
## 8. Жизненный цикл

<!-- summary: New workspace — юзер добавляет roots через выбор каталога. Валидация: не вложены друг в друга, basename уникален. Каждый root = вкладка с деревом. Open — юзер указывает путь к state-каталогу. -->
**Создание.** GUI: «New project» → пользователь выбирает **каталог** → задаёт имя проекта → добавляет roots.

Каталог — любой, куда у пользователя есть доступ. Утилита туда положит `workspace.json`, `.patchignore`, `.mcpignore`, `runtime/` и будет писать индексы. Если каталог уже содержит `workspace.json` — ошибка «здесь уже есть проект», пользователь либо открывает его, либо выбирает другой каталог.

**Добавление root'а.** Пользователь нажимает «Add root» → диалог выбора каталога. Валидация:

1. **Вложенность.** Каталог не вложен ни в один существующий root и не содержит существующий.
2. **Basename уникален.** Имя корневого каталога не совпадает с basename'ом ни одного уже добавленного root'а.
3. **Не имя Roblox-сервиса.** basename не входит в список `core.paths.ROBLOX_SERVICES`.

Если basename конфликтует, диалог показывает ошибку:

```
Дерево с корнем `toolkit` уже есть в проекте.
Второе дерево с корнем `toolkit` добавить нельзя.
Выберите каталог выше по дереву, чтобы имя отличалось
(например `project2` вместо `project2/toolkit`).
```

Утилита не придумывает альтернативу за пользователя и не предлагает автосуффиксы.

**Интерфейс — вкладки по root'ам.** Каждый добавленный root = отдельная вкладка с деревом файлов. Внутри вкладки видны только файлы этого root'а. Заголовок вкладки = basename каталога.

**Открытие.** Два пути:
- Из списка «недавние» — клик по записи, путь читается из `recent.json`.
- «Open project» → пользователь выбирает каталог. Проверяем наличие `<folder>/workspace.json`. Если нет — «здесь нет проекта».

**Удаление root'а.** Удаляется из `workspace.json`, индексы пересобираются. Если basename удалённого root'а был занят — освобождается.

**Удаление проекта.** Папку проекта удаляет пользователь (вручную или через GUI). Утилита только убирает запись из `recent.json`. Roots пользователя не трогаются никогда.

**Переименование корневого каталога root'а на диске.** basename root'а меняется. Пути в новых патчах — с новым именем. Старые патчи ломаются — это ожидаемо и осознанно. GUI показывает предупреждение при загрузке, если basename не совпадает с тем, что было в индексе.

**Переименование папки проекта.** Без последствий — все ссылки внутри `workspace.json` абсолютные к roots, к расположению папки проекта не привязаны. `recent.json` обновляется при следующем открытии через GUI.
## 9. Миграция с текущей модели

<!-- summary: Миграция не делается. Старые проекты с <project>/.patch_applier/ продолжают работать как есть. Новый workspace создаётся отдельно. -->

**Миграция не делается.** Существующие проекты с `<project>/.patch_applier/` продолжают работать как сейчас — утилита их не конвертирует, не переносит, не требует обновления. Старая модель и новый workspace живут параллельно: старый проект открывается по старому пути, новый создаётся через «New workspace».

При необходимости миграционный путь можно добавить позже, отдельным шагом. Сейчас цена выше выгоды.

## 10. Открытые вопросы

<!-- summary: Все вопросы закрыты. Модель замкнута. -->

Все ранее открытые вопросы закрыты:

1. ~~Nested roots.~~ **Закрыт.** Вложенные roots не поддерживаются (см. §4).
2. ~~MCP + FS в одном workspace — как policy?~~ **Закрыт.** MCP не подчиняется policy (см. §6).
3. ~~Совместимость `(root) [RWI]`.~~ **Закрыт.** Ключ root'а — его basename. Если root один, policy содержит одну запись; если несколько — по одной на каждый. Special-case `(root)` не нужен.
4. ~~MCP root-name в путях.~~ **Закрыт.** MCP — не root (см. §3).
5. ~~Что делать с `.patch_applier/` в старых проектах?~~ **Закрыт.** Миграция не делается (см. §9).
6. ~~Реестр vs. чистое сканирование.~~ **Закрыт.** Никакого реестра; `recent.json` — convenience (см. §7).

## 11. Инкрементальный путь

<!-- summary: Шесть шагов от дизайна до миграции. Каждый самодостаточен. -->

**Шаг 1. Дизайн (этот документ).** Согласовать модель, ответить на открытые вопросы. — **Готово.**

**Шаг 2. Config-слой, single-root external.** Ввести `Workspace` как понятие, но с одним root'ом. State — external. Остальное не трогаем. Доказательство модели на малом.

**Шаг 3. Multi-root read.** Несколько roots в `workspace.json`. Резолв путей (`<basename>/<rel>`), резолв policy. Работают только read-тулы и индексаторы. Запись — только в первый root (как сейчас по сути).

**Шаг 4. Multi-root write + per-root policy.** Полноценный write в любой root. Verify после write.

**Шаг 5. GUI-диалог workspace.** Список недавних, «New workspace», вкладки по root'ам с деревом, редактор policy, редакторы `.patchignore` / `.mcpignore` (кнопка видна только при `luau: mcp`).

**Шаг 6. Миграция.** Автоматическая конвертация старых проектов в single-root workspace (см. §9).

Каждый шаг самодостаточен, откатывается. После шага 3 можно остановиться и жить с multi-root read, если write не критичен.
