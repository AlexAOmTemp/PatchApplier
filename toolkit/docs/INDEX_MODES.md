# INDEX_MODES — режимы индекса и масштабирование
<!-- summary: Проект. Разбор проблем текущего индекса (полный × весь проект), три режима (tree / structure / full), разделение манифеста и .md, приоритеты и порядок реализации. Связан с LLMSCOPE.md (scope сужает область, режимы выбирают детализацию). -->

> **Статус:** проект. Отдельный документ, потому что описывает архитектурный сдвиг, а не точечную правку. Дополняет `LLMSCOPE.md` (scope сужает **область**, режимы выбирают **детализацию** — две независимые оси).
>
> **Аудитория:** автор утилиты.

## 1. Что не работает в текущем индексе
<!-- summary: На трёх масштабах — 180 файлов, 1000 файлов, 30k файлов — full × whole неприменим. Наблюдение из аудита: 15% сигнала, 85% шума. -->

### 1.1 Наблюдение из практики

Проведён аудит проекта из 180 модулей. Использовался `CODE_INDEX.md` (147.5 KB, 2060 строк). Что реально помогло:

- Список файлов с размерами — да.
- Маркер `⚠ large` — да. Единственный сигнал, который направил распределение усилий: `mcp.py` 1245 строк, `symbols/python.py` 1009, `gui/app.py` 902, `settings_window.py` 896.
- `◉` (has_main) — иногда.
- **Всё остальное — нет.** Symbol listings с L-диапазонами, `Hash`/`Len`, `Imports:`, `Used by:`, docstrings символов.

Соотношение: **~15% полезного сигнала, ~85% шума**. И это на 180 файлах, где обзор всего проекта — задача, которую индекс решает лучше всего.

### 1.2 На трёх масштабах

**180 файлов (текущий проект).** Full × whole = 2060 строк. Читается целиком, но 85% — не нужно. Структурный режим дал бы 180 строк.

**1000 файлов (средний проект).** Full × whole = ~11k строк, ~700 KB. Уже не читается. Структурный режим = 1000 строк, но тоже много для первого взгляда. Нужен tree.

**30000 файлов (RimWorld).** Full × whole не существует (индекс не соберётся или не влезет). Структурный режим = 30k строк — тоже нечитаемо. **Нужен tree с ограничением глубины**, где 30k сводятся к 100–200 строкам.

**Вывод.** Текущий формат хорош только на масштабе, где индекс и так не нужен. На больших проектах нужен другой формат, и это не «тот же индекс без символов».

## 2. Три оси, а не одна
<!-- summary: Детализация (tree/structure/full), область (whole/subtree), глубина. Сейчас есть только full × whole × без глубины. -->

Сейчас `get_index(kind=...)` — одна ось (какой домен: docs/code/lua). Нужно три:

| Ось | Значения | Что решает |
|---|---|---|
| **Детализация** | `tree` / `structure` / `full` | Сколько информации на строку |
| **Область** | весь проект / поддерево (`path=`) | Где смотрим |
| **Глубина** | int (только для `tree`) | Как глубоко в дерево |

`scope` (см. `LLMSCOPE.md`) — четвёртая ось, но она **ортогональна**: сужает область до рабочего набора. Не путать с `path=` — `path=` выбирает представление, `scope` фильтрует права и видимость.

## 3. Режим `tree` — карта
<!-- summary: Directory-level, ограниченная глубина, агрегаты по каталогам, маркер ⚠ на доминирующих. Для 30k файлов — 100-200 строк. -->

### 3.1 Формат
```text
toolkit/                         180 files  700 KB
  code/                          168 files  690 KB
    bridge/                        1 file   27.7 KB
    manual/                       20 files   60 KB
    toolkit/                     145 files  590 KB
      backends/                    4 files   82 KB    ⚠ largest
      config/                      6 files   46 KB
      core/                        8 files   38 KB
      formats/                     7 files   30 KB
      tools/                      24 files  220 KB    ⚠ largest
        unit/                      6 files   62 KB
        symbols/                   6 files   85 KB
      runner/                     30 files  165 KB
        gui/                       9 files  110 KB    ⚠ large
  docs/                           14 files  200 KB
  runtime/                         5 files   1 KB
```

Свойства:

- **Только каталоги, файлы не перечисляются.** Исключение — `bridge/` в примере: один файл, показать его прямо.
- **Агрегат по поддереву.** `toolkit/code/toolkit/backends/  4 files  82 KB` — 4 файла внутри (и глубже), суммарный размер 82 KB.
- **Глубина — параметр.** Дефолт для `tree` — **2**. `depth=1` — только верхний уровень, `depth=0` — корень, `depth=3` — глубже (для плоских структур).
- **`⚠ largest`** — маркер на каталоге, который доминирует на своём уровне (>30% от родителя). Не суждение, факт: «здесь больше всего».
- **`⚠ large`** — существующий маркер, если внутри есть файлы с `⚠ large` (файлы >300 строк или >16 KB). Не раскрывает какие, просто «внутри есть крупные».
- **Никаких аннотаций из scope.** Working set, целевой мод и т. п. — в `get_status`, не здесь.
### 3.2 Для RimWorld (30k файлов)
```text
RimWorld/                      30043 files  12.4 GB
  Mods/                        29978 files  12.3 GB
    0000000001/                  343 files  480 MB
    0000000002/                  287 files  220 MB
    ... (84 more)
    1201382956/                   142 files  8.2 MB
  Source/                         65 files  1.1 MB
  Data/                            0 files   0 KB
```

100–200 строк, глубина 2. Видно форму: 86 модов, один целевой. Невидно, что внутри каждого мода — для этого LLM делает `get_index(path="Mods/1201382956")`. Какой мод целевой — LLM знает из `get_status` (working set); tree этого не показывает.
### 3.3 Зачем это нужно отдельно от `survey_dir`
**tree читает файловую систему, не манифест.** Это принципиально. В примере выше под `toolkit/` есть и `code/` (Python-модули), и `docs/`, и `runtime/`. Code-манифест знает только про `.py` — если бы tree рендерился из манифеста, `docs/` и `runtime/` в нём бы не появились.

Маркеры `⚠ large` и `◉` получаются cross-reference с манифестом, **если манифест есть**. Если нет — tree работает без маркеров, просто дерево с размерами. Это позволяет использовать tree до первого rebuild.

`scope` применяется поверх walk, как `.patchignore`. Файлы и каталоги вне scope не попадают в агрегаты.

**tree vs survey_dir.** Разные инструменты, разные источники:

- `tree` — форма дерева, вложенность, контроль глубины. Источник — walk + манифест (для маркеров).
- `survey_dir` — top-N подкаталогов по количеству, разбивка по расширениям. Источник — walk, без манифеста.

`tree` отвечает на «как выглядит проект». `survey_dir` — на «из чего он состоит». Первое — про структуру, второе — про содержимое.
## 4. Режим `structure` — файлы без символов
<!-- summary: Одна строка на файл с маркерами. Для 180 файлов — 15 KB вместо 147. Для поддерева — рабочий режим. -->

### 4.1 Формат
```text
toolkit/core/patcher.py          309 стр.  12.3 KB  ◉ ⚠ large ← 5 imp → 2 users
toolkit/core/session.py           66 стр.   1.9 KB  ← 4 imp → 2 users
toolkit/core/router.py           135 стр.   4.4 KB  ← 2 imp → 3 users
toolkit/core/patchparse.py       209 стр.   6.3 KB  → 5 users
toolkit/core/paths.py             59 стр.   1.7 KB  → 13 users
toolkit/core/models.py           166 стр.   5.9 KB  → 36 users
toolkit/backends/mcp.py         1245 стр.  50.9 KB  ◉ ⚠ large ← 2 imp → 2 users
toolkit/backends/composite.py    479 стр.  18.7 KB  ⚠ large ← 2 imp → 5 users
...
```

Одна строка на файл:

- path
- lines, size
- маркеры (`◉`, `⚠ large`, `[tests/]`, `[vendor/]`, `← N imp`, `→ N users`)

Без символов, без хэшей. **Маркеры графа (`← N imp` / `→ N users`) включаются** — это file-level факты, не symbol-level, они дешёвы и позволяют отличить хаб от листа без спуска в full. Предыдущая версия этого документа говорила «без Imports/Used by» — это была ошибка, исправлено.

Размер: 180 файлов → 180 строк → ~20 KB. **В 7 раз меньше текущего.**
### 4.2 Когда это использовать

- LLM посмотрела `tree`, выбрала поддерево, хочет «что тут конкретно». Например, scope сузилась до `Mods/1201382956/`, `get_index(path="Mods/1201382956")` → 142 строки файлов. Читается целиком, даёт карту работы.
- Альтернатива — открыть `list_files` с размером, но `list_files` не знает про `⚠ large` и `◉`.

## 5. Режим `full` — файлы + символы
<!-- summary: Текущий формат. Используется редко: когда нужен symbol-level обзор большой папки. Оставить как опцию, не как дефолт. -->

### 5.1 Формат

Текущий `CODE_INDEX.md`: файлы + символы с L-диапазонами + хэши. Ничего не меняется.

### 5.2 Когда это использовать

- Аудит подсистемы (только что делали): «какие символы в `core/*`, как они связаны». Symbol-level обзор.
- Поиск «где может быть реализовано X» по именам символов без использования `find_symbol`.

### 5.3 Почему дефолт переключается

Сейчас дефолт — `full`. По наблюдениям из §1.1 это не то, что нужно в 80% сессий. Дефолт должен стать `structure`, `full` — при явном запросе.

Для поддерева: `get_index(path="toolkit/core", mode="full")` — 10 файлов с символами = 100 строк. Это работает. Full × whole был проблемой, full × subtree — нет.

## 6. Что делать с манифестом и diff
<!-- summary: Разделить источник правды (манифест) и представление (.md). Diff читает манифест, не парсит .md. Тогда любой режим рендерится на лету. -->

### 6.1 Текущее состояние

- `CODE_INDEX.manifest.json` — машиночитаемый список модулей и символов с хэшами. Питает `find_symbol`, `find_usages`, `symbol_graph`.
- `CODE_INDEX.md` — рендер того же. Читается человеком и LLM.
- `diff_code_index(prev_text, new_text)` — **парсит `.md` обратно**. Значит формат `.md` не свободен: он источник правды для diff'а.

Это причина, по которой нельзя просто «убрать символы из индекса»: diff потеряет symbol-level разрешение.

### 6.2 Как должно быть

- **Манифест** — единственный источник правды. Всегда полный.
- **`.md`** — рендерится из манифеста при запросе, с параметром `mode` и `path`. Не сохраняется как файл.
- **Diff** — читает **манифест**, не `.md`. Сравнивает структуру двух версий манифеста.

Тогда:
- `get_index(mode="tree")` — рендер из манифеста на лету.
- `get_index(mode="structure")` — другой рендер из того же.
- `get_index(mode="full")` — третий.
- Diff всегда полный (по манифесту), независимо от режима рендера.

### 6.3 Что это меняет в коде
- `indexers/code.py:build_code_index` — уже строит манифест. Рендер `.md` остаётся, но меняет роль: это **published snapshot**, а не источник данных для LLM.
- `indexers/diff.py:diff_code_index` — переписывается с парсинга `.md` на сравнение манифестов. Это тот же diff по структуре, но вход другой.
- `tools/index.py:GetIndexTool` — принимает `mode` и `path`, рендерит из манифеста на лету.
- **`.patch_applier/CODE_INDEX.md` остаётся как published snapshot.** `get_index(mode=...)` рендерит из манифеста; файл пишется на rebuild для внешних инструментов (grep, read_file) и git-trackable в чужих проектах. Источник правды — манифест, файл — проекция.

**Про аргумент «grep по нему работает».** Он слабее, чем звучал в отзыве: с активным `scope` grep по проекту и так ограничен, до `.patch_applier/` дело доходит редко. Но сам `.md` остаётся читаемым документом — `read_file` на него работает, `grep` по нему как по файлу тоже. Это не критично для LLM (она пойдёт через `get_index`), но полезно для человека в GUI и для внешних скриптов.
### 6.4 Миграция

`CODE_INDEX.md` перестаёт обновляться, потом удаляется при rebuild. Старые ссылки в LLM_START («diff индекса», «`[vN]` в CODE_INDEX.md») переформулируются: версия — в `state` рядом с манифестом, diff рендерится как сообщение в ответ на write, не как файл.

Это существенное изменение, но упрощает архитектуру: **один источник правды, одно представление — по запросу**.

## 7. Связь с `scope`
<!-- summary: Scope сужает область, режим выбирает детализацию. Ортогональны. LLM обычно: scope→subtree, mode=structure. -->

Две оси работают независимо:

- **`scope`** (см. `LLMSCOPE.md`) — «какие файлы я вообще вижу». Сужает область на уровне backend и read-тулов.
- **Режим индекса** — «в каком виде я вижу то, что вижу». Не влияет на видимость.

Типичная сессия RimWorld:

1. Пустой scope. `get_index(mode="tree", depth=2)` → форма дерева, 100 строк.
2. LLM решает работать в `Mods/1201382956`. `add_scope("/Mods/*", "!/Mods/1201382956")`.
3. Scope активен. `get_index()` → дефолт `structure`, теперь по scope = 142 файла, 142 строки.
4. LLM работает. `get_index(path="Mods/1201382956/Defs", mode="full")` → символы в Defs, ~50 строк.

Никаких противоречий, оси дополняют друг друга.

## 8. Приоритеты и порядок
<!-- summary: Четыре шага — tree, structure, разделение манифеста, diff. Плюс один эксперимент перед началом. -->

### 8.1 Что делать первым

**Эксперимент перед началом:** сгенерировать `tree` и `structure` для текущего проекта (180 модулей) из существующего индекса. Оценить:

- Сколько строк, сколько KB?
- Теряется ли что-то, к чему привык?
- Если LLM-сессия начинается с `tree`, на каком шаге нужен `structure`, на каком `full`?

Это часы работы и даёт ответ, нужно ли всё остальное. Делать до правок кода.

### 8.2 Если эксперимент удался

1. **`get_index(mode="structure")`** — фильтр существующего рендера на лету. Без изменения архитектуры. Один тул, одна правка в `GetIndexTool`.
2. **`get_index(mode="tree", depth=N)`** — новый рендер из тех же данных. Небольшая функция в `renderer.py`.
3. **`get_index(path="...")`** — срез по поддереву. Фильтр входного списка модулей по префиксу пути.
4. **Разделение манифеста и `.md`** — большая правка. Делать только после того, как режимы 1–3 работают и подтверждены на реальном использовании.
5. **Diff по манифесту** — часть шага 4.

### 8.3 Что не делать
**Решение:** `get_index(kind=..., mode=...)` — `mode` **обязателен**. Три режима — это три разных ответа на один и тот же вопрос «дай обзор», и делать вид, что один из них «по умолчанию правильный», значит закладывать путаницу.

Прецедент в коде: `replace_unit` без `part` и `block` возвращает `scope_required` — не потому что нет «разумного дефолта», а потому что без явного указания LLM не знает, что получит. То же здесь.

**Почему не контекстные дефолты** (`path=` → structure, whole → tree). Набор правил «в какой ситуации какой дефолт» требует держать в голове больше, чем одно правило «mode обязателен». Каждое правило — точка расхождения между сессиями: одна сессия запомнит, другая нет, третья удивится.

**Почему не сессионный дефолт.** Это второй способ получить тот же набор правил, только теперь с состоянием. Persistence дефолта в `.patch_applier/config.json` или в state — ещё одна персистентная сущность, которую надо объяснять пользователю. Ноль выгоды против одного обязательного параметра.

**Что если `mode` станет шумным.** Если по опыту LLM в 80% случаев зовёт `get_index(mode="structure")`, это сигнал, что нужен не дефолт, а **пересмотр набора режимов**: возможно, `structure` — это и есть «то, что LLM называет `get_index`», и нужен отдельный тул `get_index_tree` / `get_index_full` для остальных случаев. Решать по факту.
## 9. Открытые вопросы
<!-- summary: Четыре — глубина по умолчанию, дерево vs список, что показывать на листьях, как считать размер. -->

### 9.1 Дефолтная глубина `tree`

3 — эмпирика. На глубоких проектах (`a/b/c/d/e/f/g`) может быть мало; на плоских (`src/*.py`) — много. Не решать сейчас, выяснить на реальных проектах.

### 9.2 Дерево vs список

`tree` — иерархия с отступами. Альтернатива — плоский список каталогов с префиксами (`toolkit/code/toolkit/backends/`). На 30k файлов плоский список был бы длиннее, но лучше grep-ается. Решить после эксперимента.

### 9.3 Что на «листьях» дерева

Каталог с 1–3 файлами: показывать сами файлы или агрегат? Сейчас в примере `bridge/ 1 file 27.7 KB` — агрегат. Но если файл всего один, показать его имя может быть полезнее: `bridge/bridge.py 625 стр. 27.7 KB`. Правило: **файл показывается, если он единственный в каталоге, либо если каталог на последнем уровне глубины**.

### 9.4 Агрегированный размер

`size` для каталога — сумма размеров всех файлов ниже? Или только прямых детей? Пользователю важнее полная сумма, но её нельзя сравнивать с `⚠ large` (>16 KB порог на файл). Нужно явно разделить: `(N files, M KB, ⚠ if any file inside is large)`. Не решать сейчас.

## 11. Эксперимент на реальном проекте
<!-- summary: Рендер из существующего CODE_INDEX.md. Full 2066 строк / 146 KB, structure 181 строка / 18 KB, tree 15 строк / 0.8 KB. Режимы подтверждены. Дополнительные наблюдения. -->

### 11.1 Метод

Скрипт `toolkit/code/manual/index_modes_demo.py` читает существующий `.patch_applier/CODE_INDEX.md` (181 модуль) и рендерит его в двух режимах без изменения самого индекса. Полный вывод — в истории сессии; ниже — сравнение и наблюдения.

### 11.2 Метрики

| Режим | Строк | Размер | Сжатие |
|---|---|---|---|
| **full** | 2066 | 146 461 B | 1× (baseline) |
| **structure** | 181 | 18 678 B | **7.8× меньше** |
| **tree (depth=3)** | 15 | 834 B | **175× меньше** |

На 181 модуле full читается целиком, но использует 15–20% сигнала (наблюдение из §1.1). Structure помещается в один экран и содержит весь сигнал, который был востребован при аудите. Tree — 15 строк, читается мгновенно.

### 13.2 Решения по спорным

**1. `← N imp` / `→ N users` в structure — включать.** §4.1 и §11.4 в предыдущей версии противоречили друг другу. Включение обосновано: это file-level факты, не symbol-level, они дешёвы и позволяют отличить хаб от листа без спуска в full. Исправлено в §4.1.

**2. `mode` — обязательный параметр, без дефолта.** Контекстные дефолты (`path=` → structure, whole → tree) отвергнуты. Сессионный дефолт отвергнут по той же причине. Набор правил «в какой ситуации какой дефолт» требует держать в голове больше, чем одно правило «mode обязателен», и каждое правило — точка расхождения между сессиями. Прецедент: `replace_unit` без `part`/`block` → `scope_required`. См. §8.3.

**3. Дефолтная глубина tree — 2, не 3.** На RimWorld depth 2 даёт 86 модов — этого достаточно для reconnaissance. Depth 3 уйдёт внутрь каждого мода, и 30k файлов дадут сотни строк, а не 15. На toolkit depth 3 дал 15 строк только потому, что структура плоская; для игровых корней с глубокой вложенностью это не масштабируется. Исправлено в §3.1.

**4. On-disk `.md` — остаётся как published snapshot.** `get_index(mode=...)` рендерит из манифеста на лету; файл пишется на rebuild для внешних инструментов и git. Источник правды — манифест. Аргумент «`grep` по нему работает» слабее, чем звучал: с активным `scope` grep по проекту ограничен, но сам `.md` остаётся читаемым документом. Исправлено в §6.3.

**5. Откуда tree берёт данные — FS walk + cross-reference с манифестом.** В tree-примере видны `docs/` и `runtime/`, которых нет в code-манифесте. Если tree рендерится из манифеста — эти каталоги исчезнут. Значит tree — walk. Маркеры `⚠ large` и `◉` — из манифеста, если он есть. Если нет — tree работает без маркеров. Исправлено в §3.3.

**6. `⚠ working set` в tree-примере — убрано.** Это аннотация из scope, не из FS. Working set показывается в `get_status`, не в tree. Читатель не должен думать, что tree сам умеет определять рабочий набор. Исправлено в §3.1 и §3.2.

**7. `list_units` в модели масштабов.** Не «четвёртый режим», а завершение лестницы: tree (проект) → structure (поддерево) → `list_units` (файл) → `read_unit` (unit). Всё ниже structure уже есть в коде, документ просто не описывал это как часть модели. В §8.2 добавлено в шаги.

**8. docs и Lua индексы — та же ось режимов.** Отличия в маркерах и формате, не в осях:

- **docs (`INDEX.md`):** tree — оглавление (файлы → секции → подсекции), structure — файлы с числом секций, full — текущий (с summary и тегами).
- **Lua (`CODE_INDEX_LUA.md`):** tree / structure / full как у Python. Особенность: 267 модулей дают 861 символ (3.2 символа/модуль), у Python — 181 модуль на 1228 символов (6.8). Пропорция символов к модулям ниже, `structure` для Lua сожмётся чуть меньше, но режимы применяются без изменений.

**9. `unit_proto/` — отдельная задача.** Уборка `manual/` (старая версия `tools/unit/`), не относится к режимам индекса. Отдельный тикет для LLM-сессии.

### 13.3 Что осталось открытым

- **Snapshot: писать ли на rebuild всегда или только по запросу.** Если LLM никогда не открывает `.md` напрямую — можно не писать на каждом rebuild. Пока — писать (для внешних инструментов и git). Решать по факту.
- **Плоский список vs дерево для `tree` (§9.2).** Не решать сейчас — на 180 файлах разницы нет, на 30k нужен эксперимент.
- **Агрегированный размер (§9.4).** Пока — сумма всех файлов поддерева. Формат строки: `backends/ 5 files 89 KB (mcp.py 51 KB) ⚠3 large` — общий размер, крупнейший файл, число `⚠ large` внутри. Это чуть изменённый формат против §3.1; в реализации — использовать этот, обновить §3.1 после подтверждения.
