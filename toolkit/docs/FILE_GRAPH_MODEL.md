## 1. Что это
<!-- summary: Не индекс и не survey_dir, а единая файлово-графовая модель с четырьмя слоями (FS / структурный / графовый / метаданные), реестром маркеров и инкрементальным rebuild. Два канала к LLM: pull (query) и push (diff). Push — главный. -->

Не индекс и не survey_dir, а единая файлово-графовая модель с четырьмя слоями (FS / структурный / графовый / метаданные), реестром маркеров и инкрементальным rebuild. Два канала к LLM: pull (query) и push (diff). Push — главный.

**Index и survey_dir — один механизм, неправильно разрезанный на два.** Оба дают обзор, оба читают FS, оба знают про scope. Различаются тем, что индекс персистентный и знает про граф, а survey_dir строится на лету. Разница — не в природе, а в политике сборки.

Правильно — **одна модель**, у которой есть слои. Что не построено — берётся live-walk. Что построено — уже готово. Запрос не думает о том, откуда данные.

**Модель — не документ для чтения.** Это **анализатор** с двумя каналами к LLM:

- **Pull** — LLM спрашивает («покажи дерево `Mods/`»). Вторичный канал, нужен для навигации.
- **Push** — модель сигнализирует о том, что изменилось. Главный канал. LLM узнаёт о проблемах **до** того, как их запросит.

Именно push делает всё это нужным. Без него индекс — просто карта. С ним — **детерминированный контролёр**, который следит за состоянием проекта и привлекает внимание к подозрительному.

## 2. Слои
<!-- summary: Четыре слоя — FS, структурный, графовый, метаданные. Полнота по слоям зависит от того, есть ли адаптер для формата. -->

Модель многослойная. Каждый слой знает разное и строится разными средствами.

### 2.1 FS-слой

Знает: файлы, каталоги, размеры, расширения, mtime.

**Строится live-walk**, не персистится. Walk быстрый, mtime узнаётся на месте.

**Применим ко всем файлам** — включая `.dll`, `.png`, всё, что не парсится.

**Используется для:** ориентации, tree, scope-фильтрации, «где что лежит».

### 2.2 Структурный слой

Знает: unit'ы (functions, classes, sections, XML-элементы), их границы, части (head/annotation/body), границы блоков.

**Персистится** — парсинг стоит времени. Хранится в структурированном виде (сейчас — манифест, но контент шире).

**Применим к форматам с адаптером.** Python, Lua, Markdown — есть. XML, C#, JS — надо добавить. Файлы без адаптера в этом слое отсутствуют.

**Используется для:** `list_units`, `read_unit`, `replace_unit`, diff по символам.

### 2.3 Графовый слой

Знает: импорты, вызовы, рёбра между unit'ами, циклы, hub'ы (`→ N users`), обратные зависимости.

**Персистится**, строится из структурного слоя.

**Применим к форматам, для которых структурный слой есть и для которых можно извлечь рёбра** (Python — да, XML — частично через `ParentName`/`defName`, JS — да).

**Используется для:** `find_usages`, `symbol_graph`, hub-маркеров, cycle-маркеров, blast radius.

### 2.4 Метаданные

Знает: хэши unit'ов и файлов, mtime последнего изменения, stale-summary флаги, версии (см. §5), исторические снимки.

**Персистится.** Это то, что делает push возможным.

**Применим к тем же файлам, что структурный слой** (нужны unit'ы, чтобы следить за их изменениями).

**Используется для:** diff, stale-детекции, истории.

## 3. Парадигма: push, а не pull
<!-- summary: Модель показывает проблемы сама. Push = diff между двумя версиями модели. Маркеры stateless (см. §14.6), diff сигналов — уровень системы. Композиции маркеров дают качественно другие сигналы, чем одиночные. -->
<!-- summary: Push — гипотеза, не подтверждённый факт. Проверяется вертикальным срезом на 3–4 сигналах «сломано». Сигналы делятся на hard (push всегда), soft (с лимитом), hygiene (не пушить). -->

### 3.1 Что уже проверено

Метка `⚠ stale` работает: LLM видит её в диффе после write и идёт исправлять. Это наблюдалось в реальных сессиях. Один сигнал, один проект, ограниченный класс задач.

### 3.2 Что не проверено

**Push как парадигма — гипотеза.** Из «один сигнал работает» не следует «20 сигналов работают». Риск тот же, с которого начинался INDEX_MODES: шум, только теперь он приходит незапрошенным после каждого патча.

Никто не проверял, что LLM **полезно** реагирует на сигналы. Возможные сценарии, все правдоподобные:

- LLM читает сигнал и реагирует — гипотеза верна.
- LLM игнорирует сигналы после 3–4 патчей — шум.
- LLM реагирует на одни типы и игнорирует другие.
- LLM реагирует, но неверно — «`unused-symbol` — удалить» может привести к удалению используемого через рефлексию.

**Проверяется вертикальным срезом.** Не строить реестр, композиции, авто-discovery. Сделать минимум: инкрементальный rebuild → per-patch diff с 3–4 сигналами → прогон на реальных задачах → лог реакции LLM. По результатам — решать про остальное.

### 3.3 Сигналы разной природы

Не все сигналы одинаковы. Три класса, разное поведение в push.

**Hard — сломано.** Push всегда, без лимита.

- `api-change` — сигнатура публичного символа изменилась, и есть вызывающие вне патча. **Самый ценный сигнал.** Классический случай тихой поломки: `replace_unit(part="head")` поменял параметры, callers в другом файле не в патче, LLM не увидит, пока не запустят.
- `xml-parent-missing` — Def ссылается на несуществующий `ParentName`.
- `new-cycle` — в графе импортов появился цикл.
- `broken-ref` — документ ссылается на удалённый символ.

**Soft — проверь.** Push с лимитом (не все сразу, приоритет по серьёзности).

- `stale` — summary не совпадает с телом. Не поломка, но требует реакции.
- `stale-docstring` — параллель к stale для docstring.
- `hub-new` — модуль стал hub'ом. Контекст для осторожности.

**Hygiene — не пушить.**

- `large` — размер превысил порог. Не относится к задаче патча.
- `unused-symbol` — символ никто не вызывает. В динамическом Python — ложные срабатывания, при XML-ссылках — тем более. **Не пушить.** Если нужно — pull.
- `churn` — частые изменения. Сигнал для архитектурного анализа, не для правки.

**Правило:** hard — push. Soft — push с лимитом. Hygiene — только pull.

### 3.4 Почему это важно

Сейчас LLM должна **сама** знать, что искать: «а нет ли тут цикла», «а не стал ли этот символ hub'ом». Это невозможно — она не помнит состояние между патчами.

С push-парадигмой модель **следит за hard-сигналами** и сообщает только об изменениях. Работа LLM — реагировать, а не помнить. Но работает это только для hard-сигналов — soft и hygiene добавляются, если данные покажут пользу.

### 3.5 Отношение к «запросу»

Query (pull) остаётся. Нужен для навигации: «покажи дерево», «прочитай unit», «найди символ». Push — для изменений, которые легко пропустить без внешнего сигнала.

**Три уровня push:**

- **Одиночный hard-сигнал появился.** `⚠ api-change: helper (2 callers вне патча)`. Детерминированный сигнал от одного маркера.
- **Композиция сработала.** `⚠ risk-large-hub`. Правило над сигналами, качественно другой смысл (§14.3).
- **Diff между версиями.** Система сравнивает `signals(v_n)` и `signals(v_{n+1})`, показывает разницу. Маркер не знает про diff (§14.6).

Первые два — про то, что показать. Третий — про то, когда показать. Push работает на всех трёх уровнях.
## 4. Diff как основной канал
<!-- summary: Diff рендерится из модели, не из .md. Показывает не только «что изменилось», но и «какие маркеры появились/исчезли». Это и есть push. -->

### 4.1 Текущее состояние

`diff_code_index` парсит `.md` обратно. Формат `.md` залочен. Сигналы в диффе — только изменения структуры (модули, символы), без метаданных и графа.

### 4.2 Как должно быть

Diff читает **модель**, не `.md`. Сравнивает два состояния модели:

- структурный слой → добавленные/удалённые/изменённые unit'ы
- графовый слой → новые/пропавшие рёбра, новые hub'ы и циклы
- метаданные → новые/снятые сигналы (stale, large, unused)
- FS-слой → добавленные/удалённые/переименованные файлы

Результат — **один текст**, где сигналы смешаны с изменениями:

```
~ toolkit/core/models.py  (+3 стр.)
    ~ Symbol    L84-L112 (изменён)
    ⚠ api-change: helper (2 callers вне патча) — обнови вызывающих
    ⚠ hub +1 (→ 36 users)

+ toolkit/core/new_thing.py
    ◉ main

~ docs/WORKSPACE.md  §3.2
    ⚠ stale — тело менялось, summary нет

- toolkit/core/old_helper.py
    ⚠ removed — был hub (← 3 imp)
```

Это не «список изменений». Это **сигнальная сводка**, где LLM видит и что поменялось, и что из этого опасно.

### 4.3 Дифф на уровне операции vs дифф на уровне патча
Два вида:

- **Per-write** — что изменила конкретная операция. Возвращается в `Result.message` write-тула. Малый, точный. Не для «прочитать всё», а для «понять, что я только что сделал».
- **Per-patch** — что изменилось за весь патч. Общий, в `##RESULT`. Именно здесь push-сигналы собираются вместе.

Per-write сейчас есть (счётчики `delta`). Per-patch — сейчас нет, только `##RESULT` со счётчиками ok/error.

Правильная форма per-patch: **изменённые файлы + сигналы, появившиеся в них**. Формат — в §9.1. Отдельная секция «косвенные маркеры» — файлы вне патча, затронутые через граф (например, `b.py` стал hub'ом, потому что `a.py` начал на него ссылаться).

Диффы не раздуваются обратно до «покажи всё»: push-парадигма (§3) означает, что diff показывает **изменения сигналов**, а не все сигналы. Что не изменилось — не показывается.
## 5. История (git-подобная)
<!-- summary: Модель хранит версии. Diff между любыми двумя версиями, не только текущей и предыдущей. Закрывает «что изменилось, пока я не смотрела». -->

### 5.1 Идея

Каждый rebuild создаёт **версию модели**. Версии нумеруются монотонно. Каждая содержит:

- снимок структурного слоя (unit'ы + хэши)
- снимок графового слоя (рёбра, hub'ы, циклы)
- снимок метаданных (stale-флаги, сигналы)

Diff возможен **между любыми двумя версиями**, не только «текущая vs предыдущая»:

```
diff(from=v42, to=v57)
```

Это решает проблему, которую мы обсуждали: «LLM не помнит, что изменилось, пока она не смотрела». С push-парадигмой это ещё и автоматизируется: при старте новой сессии модель показывает diff между последней виденной версией и текущей.

### 5.2 Что это даёт

- **«Что изменилось с прошлого раза».** Одним запросом.
- **«Когда появился этот hub».** Прослеживается по истории.
- **«Что откатилось».** Если что-то исчезло — видно в diff между версиями.
- **«Что было 10 версий назад».** Модель помнит, не только текущее.

### 5.3 Как это делать

Сейчас в коде: `bump_seq` в `indexers/state.py`, `.version` файлы рядом с индексами. Это зачаток.

Правильно: **одна история на модель**, не отдельные `.version` на каждый домен. Каждая версия — маленький снимок (только то, что изменилось). Старые версии можно уплотнять (раз в N версий — полный снимок, между — delta).

Git как зависимость не нужен — структура модели линейная (не ветвится), монотонная. Достаточно append-only log + периодические snapshot'ы.

## 6. Query API (pull)
<!-- summary: Один тул query(view, path, scope). Виды: tree, symbols, graph, metadata, history. Заменяет get_index, survey_dir, list_files. -->

### 6.1 Один тул, разные view

```
query(view="tree", path="Mods/1201382956/", scope=True)
query(view="symbols", path="toolkit/core/patcher.py")
query(view="graph", node="GrepTool.execute")
query(view="metadata", path="toolkit/core/")
query(view="history", from=42, to=57)
```

`view` обязателен — прецедент `replace_unit` с `part`/`block`. Дефолтов нет, чтобы не создавать путаницу «в какой ситуации какой дефолт».

### 6.2 Что показывает каждый view
**`files`** — файловый уровень, FS + структурный. Одна строка на файл: `path`, `lines`, `size`, маркеры `◉`, `⚠ large`, `[tests/]`, `[vendor/]`, `← N imp`, `→ N users`. Это рабочий вид для точечной работы — то, что в INDEX_MODES называлось structure. Рекурсия по поддереву с лимитом вывода.

**`tree`** — FS-слой, директории. Агрегаты (файлов, подпапок, размер, расширения), маркеры `large`/`tests`/`vendor`. Рекурсия до лимита вывода, не по глубине. Работает для всех файлов, включая `.dll`.

**`symbols`** — структурный слой. Файл → unit'ы → части. Для файлов без адаптера — ошибка «формат не парсится».

**`graph`** — графовый слой. Узел + callers + callees + blast radius. Только для распарсенных файлов.

**`metadata`** — метаданные. Хэши, mtime, stale-флаги, сигналы на файл/unit.

**`history`** — разница между версиями.

**Лестница.** `tree` (весь проект) → `files` (поддерево) → `symbols` (файл) → `read_unit` (unit). Каждый следующий шаг требует явного адреса и даёт больше деталей. `graph` и `metadata` — ортогональны, отвечают на другие вопросы.
### 6.3 Что это заменяет
**Заменяет:**

- `get_index(mode=...)` → `query(view=tree|symbols|... , path=...)`
- `survey_dir` → `query(view="tree", ...)`
- `list_files` → `query(view="tree", ...)`
- `list_units` → `query(view="symbols", path=file)`
- `symbol_graph` → `query(view="graph", node=...)`
- `find_usages` → `query(view="graph", node=..., edges="in")`

**Добавляет новые view:**

- `markers` — реестр маркеров. `query(view="markers")` — все, `query(view="markers", name="large")` — полное описание одного (§14.4).
- `rules` — композиции. `query(view="rules")` — какие правила активны, что каждое детектит (§14.3).

**Остаётся отдельным:**

- `read_unit` — возвращает текст, не структуру.
- Все write-тулы.
- Все search-тулы (`grep`, `find_symbol`).

Полный список — в §11.
## 7. Scope
<!-- summary: Две директивы в одном файле: `+` (scope, query-time) и `-` (skip из модели, build-time). Пишет LLM, не пользователь. `.patchignore` остаётся security-границей. -->

Две директивы в одном файле: `+` (scope, query-time) и `-` (skip из модели, build-time). Пишет LLM, не пользователь. `.patchignore` остаётся security-границей.
### 7.1 Две разные оси

Раньше мы называли «scope» один механизм. На деле их два, и они решают разные задачи.

**Ignore** — файл не парсится. Модель знает только FS-слой: имя, размер, mtime. Нет unit'ов, нет рёбер графа, нет метаданных. Файл виден в `query(view="tree")` с маркером `[not indexed]`, но `query(view="symbols")` для него вернёт ошибку «формат не индексируется».

Применяется при **build**. Игнорируемые файлы никогда не попадают в структурный, графовый, метаданные слои.

**Scope** — фильтр при query. Модель построена полностью, но LLM видит подмножество. `query(view="tree")` со scope не показывает файлы вне scope, хотя модель про них знает.

Применяется при **query**, не при build.

### 7.2 Почему нужно и то, и другое

**Пример: Unity-проект.** `Assets/Plugins/` — 40 000 файлов сторонних библиотек, `Assets/ThirdParty/` — 30 000. Пользователь в них никогда не работает. Что делать?

Если только **scope**: модель всё равно парсит 70k файлов. 60–120 секунд на первый rebuild, память под структурный слой, бесполезный граф, метаданные, которых никто не читает. `query(view="tree")` их не покажет, но они есть.

Если только **ignore**: модель парсит только рабочие 30k. Но при работе с несколькими задачами (сейчас gameplay, завтра UI) — нужен способ переключать область видимости без потери модели.

**Оба.** Ignore убирает плагины из модели совсем. Scope переключает видимость внутри модели.

### 7.3 Формат `.llmscope`
Один файл, две директивы. Пишет **LLM**, не пользователь. Пользователь `.llmscope` вообще не трогает — при необходимости видит содержимое через `get_status`.

```
# Работаю в Scripts
+ Assets/Scripts/**

# Плагины — 70k файлов, не нужны в модели
- Assets/Plugins/**
- Assets/ThirdParty/**

# Library кэш Unity, никогда
- Library/**

# Память исследования
# Assets/OldSystem — просмотрен, удалён в v2
```

**`+` = scope.** Если есть хотя бы одно `+` — видно только совпавшее. Если `+` нет — видно всё.

**`-` = skip из модели.** Не парсить. Файл остаётся в FS-слое (виден в tree), но не в структурном, графовом, метаданных.

**`!` = negation.** Снимает предыдущее правило. Как в `.patchignore`.

**`#` — комментарий**, сохраняется. Для памяти исследования.

### Приоритет при конфликте
**`-` всегда сильнее `+`.** Если путь исключён через `-`, никакое `+` его не вернёт. Если нужно вернуть — снять `-` или добавить `!pattern`.

Это несимметрично, и намеренно. `-` — решение «не парсить», `+` — «работаю тут». Расширение области работы не должно расширять модель, если пользователь явно что-то исключил.

```
+ Assets/Scripts/**
- Assets/Scripts/Old/**
```

Результат: `Assets/Scripts/Old/` не парсится (сильнее), остальное в `Scripts/` — в модели и видно.

**Порядок внутри одной директивы.** Последнее правило выигрывает, как в `.patchignore`. Внутри `-` и внутри `+` — отдельные списки, конфликты разрешаются порядком строк.

**Не как в `.gitignore`.** Там работает принцип «специфичное правило побеждает» (более глубокий путь сильнее более общего). Здесь другое правило: `-` побеждает `+` независимо от специфичности. Это разные модели конфликта, не путать.
### Пример: negation

```
- Assets/Plugins/**
! Assets/Plugins/MyCustomTool/**
```

Результат: всё в `Plugins/` исключено из модели, кроме `MyCustomTool/` — он парсится.
### Семантика пустого файла

Пустой или отсутствующий `.llmscope` — видно всё, парсится всё. Это норма для начала работы.

### Кто пишет

**LLM.** Она видит проект через `survey_dir`, понимает архитектуру (Unity, RimWorld, микросервисы), знает, что делает в этот момент. Пишет правила через `set_scope`.

**Пользователь** не пишет `.llmscope`. Он может посмотреть содержимое через `get_status` и поправить руками, но это не штатный путь. Если LLM ошибается с scope — пользователь увидит в статусе и скажет «поправь».

**Почему не `include-only` / `exclude-only`.** Две директивы нужны вместе:

- `-` для «не парсить вообще» (70k плагинов Unity — экономия build-времени и памяти).
- `+` для «работаю тут» (переключение между задачами без потери модели).

Одна директива не покрывает оба случая.
### 7.4 Отношение к `.patchignore`
Два независимых механизма с разной природой.

**`.patchignore`** — security-граница, пишет человек. Файлы не читаются и не пишутся вообще. Backend возвращает `hidden_path` при любой операции. Дефолт: `.*`, `__pycache__`, `node_modules`, `venv`.

**`.llmscope`** — рабочая область, пишет LLM. Файлы существуют для backend, но могут быть исключены из модели или из видимости.

| | `.patchignore` | `.llmscope -` | `.llmscope +` |
|---|---|---|---|
| Кто пишет | человек | LLM | LLM |
| Природа | security | build-политика | рабочая область |
| Backend читает | нет | да | да |
| FS-слой (tree) | нет | да | да |
| Структурный слой | нет | нет | да |
| Видно в query | нет | нет | да |

### Почему LLM решает про skip

Раньше думали: «пользователь должен понимать разницу между exclude-from-view и exclude-from-model». Но `@.llmscope` — файл, который пишет LLM. Пользователь видит результат в `get_status` и при необходимости поправляет.

Значит **уровни — сложность для LLM, не для пользователя**. LLM справится с двумя директивами (`+` и `-`), потому что:

- Она видит проект (Unity-плагины, RimWorld-моды) и понимает, что с чем делать.
- Она знает, что делает в этот момент (работа в `Scripts/` сейчас, не в `Plugins/`).
- Если ошибается — пользователь поправит или она сама пересмотрит через `get_scope`.

Пользователь не выбирает между тремя концептами. Их нет для него. Они есть для LLM, которая решает, что записать в файл.

### Пример: широкий корень

Пользователь-чайник указал `C:\UnityProject\` вместо `C:\UnityProject\Assets\Scripts\`. Проект видит 70 000 файлов, из которых 68 000 — плагины.

LLM:

1. `survey_dir("")` → видит распределение: `Library/` 30k, `Assets/Plugins/` 40k, `Assets/Scripts/` 500.
2. Решает, что работать нужно в `Scripts/`.
3. `set_scope("+ Assets/Scripts/**\n- Library/**\n- Assets/Plugins/**")`.
4. Модель парсит 500 файлов, всё остальное в FS-слое.

Пользователь не участвовал. Если он хочет поправить — увидит в `get_status` строку scope и скажет «нет, не так». Но обычно не надо.
### 7.5 Инвалидация при смене корней

Как в §2.2 DECISIONS: тихо игнорировать. Правило, ссылающееся на удалённый корень, не матчится. Когда корень вернётся — заработает.

### 7.6 Не security-boundary

Scope и ignore — не граница безопасности. LLM может снять их одним `set_scope("")`. Пользователь увидит в `get_status`, что scope не тот. Не блокирует. `.patchignore` остаётся security, `.llmscope` — UX.
## 8. Adapters
<!-- summary: Один rebuild, один манифест, N адаптеров. Python/Lua/MD есть. XML, C#, JS — добавить. Единый Unit-контракт. -->

### 8.1 Единый контракт

Уже есть в `tools/unit/`: `Unit(name, qualname, kind, line_start, line_end, head, annotation, body, blocks)` — общий тип для всех форматов. Три адаптера (`adapter_py`, `adapter_lua`, `adapter_md`) строят его из разных источников.

**Добавление формата = добавление адаптера.** Не бэкенда, не индекса, не rebuild-тула. Один файл.

### 8.2 Реестр

Сейчас `_build` в `unit/reader.py` хардкодит `if ext == ".py"`. Заменить на реестр:

```python
ADAPTERS = {
    ".py": adapter_py,
    ".lua": adapter_lua,
    ".luau": adapter_lua,
    ".md": adapter_md,
    ".xml": adapter_xml,   # будет
    ".cs": adapter_cs,     # будет
    ".js": adapter_js,     # будет
}
```

`list_formats` — что поддерживается. `query(view="tree")` показывает расширения в агрегатах, а рядом — маркер «парсится»/«не парсится».

### 8.3 Что нужно для XML (RimWorld)

`adapter_xml.py`: Defs как Unit tree.

- `qualname` = `defName` или путь по родителям (`Defs.ThingDef.Wall`).
- `kind` = `def` / `patch` / `node`.
- `blocks` = дочерние элементы.
- `annotation` = `<label>` или `<description>`.
- Рёбра графа = `ParentName` (наследование), `defName` (ссылки).

Простой XML — не tree-sitter, `xml.etree` достаточно. RimWorld Defs структурированы, не arbitrary XML.

### 8.4 Что нужно для C#

`adapter_cs.py`: Roslyn-подобный парсер или tree-sitter-c-sharp.

- namespace / class / method — Unit'ы.
- `qualname` = `Namespace.Class.Method`.
- Аннотации = XML-doc-comments (`/// <summary>`).

Для C# tree-sitter предпочтительнее — грамматика стабильная, есть в стандартном наборе.

## 9. Diff между версиями
<!-- summary: Из истории, не из .md. Показывает изменения структуры + новые сигналы. Основной канал push. -->

### 9.1 Формат

Diff двух версий модели:

```
=== DIFF v42 → v57 ===

~ toolkit/core/models.py  (+3 стр.)
    ~ Symbol  L84-L112 (изменён)
    ⚠ hub +1 (→ 36 users)

+ toolkit/core/new_thing.py
    ◉ main

~ docs/WORKSPACE.md  §3.2
    ⚠ stale
```

Секции:

- **Структура.** Что появилось, что исчезло, что изменилось. Per-file, per-unit.
- **Сигналы.** Новые hub'ы, cycle, large, stale, unused-symbol, broken-ref. Собраны отдельно — чтобы LLM видела их без прокрутки.
- **Резюме в шапке.** `[~3 +1 -2 ⚠hub+1 ⚡cycle+1]` — короткая сводка.

### 9.2 Когда вызывается

- **Автоматически после write-патча** — общий diff в `##RESULT`.
- **При запросе** `query(view="history", from=N, to=M)` — между любыми версиями.
- **При старте сессии** — модель показывает diff между последней виденной и текущей.

Третий пункт — самая ценная часть. Именно он закрывает «LLM не помнит, что было в предыдущей сессии».

## 10. Что не решает
<!-- summary: Границы модели. Чего она не умеет и что остаётся на LLM или других тулах. -->

Модель — анализатор, но не всеведущий.

- **Не понимает семантику.** Не знает, что «крафт блоков» относится к `ThingDef` в `Mods/1201382956`. Только сопоставляет имена и рёбра. Semantic search — отдельная задача, отложена.
- **Не заменяет чтение.** Модель говорит «здесь hub», но что в нём — надо читать. `read_unit` остаётся.
- **Не верифицирует намерения.** Тул сделал ровно то, что записано в аргументах. Модель не знает, чего хотела LLM. Push-сигналы — про изменение состояния проекта, не про соответствие намерению.
- **Не покрывает всё.** Форматы без адаптера — только FS-слой. Только tree, размер, mtime.
- **Не выполняет код.** Поведенческий анализ — не наша задача.

## 11. Что это отменяет
<!-- summary: Список того, что уходит. Обратная совместимость не важна. -->
С полным отказом от обратной совместимости:

- **`survey_dir`** — становится `query(view="tree")`.
- **`get_index(mode="full")`** — не нужен. Полный `.md` индекс уходит.
- **`get_index(mode="structure")`** — становится `query(view="symbols", path=...)` для поддерева, но без символов, только файлы. Или просто `view="tree"` с агрегатами.
- **`.patch_applier/CODE_INDEX.md`** — удаляется. Не нужен, если diff читает модель.
- **`.patch_applier/INDEX.md`** — то же для docs. Рендер по запросу.
- **`list_files`** — `query(view="tree")` без рекурсии.
- **`list_units`** — `query(view="symbols", path=file)`.
- **Три отдельных манифеста (docs / code / lua)** — один общий манифест модели.
- **`index_docs` / `index_python` / `index_lua`** — флаги не нужны, адаптеры решают, что парсится.
- **`rebuild_index` / `rebuild_code_index` / `rebuild_lua_code_index`** — один `rebuild` модели.

Что остаётся:

- Все write-тулы (`replace_unit`, `replace_in_file`, `grep_replace`, ...).
- Все search-тулы (`grep`, `find_symbol`, `grep_replace_mcp`).
- `read_file`, `read_unit` — это не «обзор», это чтение.
- `run_python`, `verify_syntax`, `file_stat` и прочие точечные.
- MCP-тулы для Lua — весь bridge-стек.
## 12. Открытые вопросы
<!-- summary: Пять — история, scope, ребилд, адаптеры, миграция. -->
### 12.1 Закрыто в этой версии

Раньше были открытыми — теперь решены:

- **История** — одна на модель, append-only log + периодические snapshot'ы (§5.3). Не три истории на три домена.
- **Инкрементальный rebuild** — предусловие, не оптимизация (§15.1). Первый шаг миграции.
- **Маркеры stateless, diff — уровень системы** (§14.6).
- **Композиции — отдельный слой над сигналами** (§14.3).
- **Snapshot — read-only view** (§14.2). Маркер не получает доступ к модели.
- **Реестр маркеров — auto-discovery** (§14.4). Новый маркер = новый файл.

### 12.2 Адаптеры — кто первый после Python/Lua/MD

XML для RimWorld или C# для Unity-стека? Зависит от того, какой проект первый потребует. XML выглядит проще: `xml.etree`, не нужен tree-sitter, структурно прост. C# — tree-sitter, но зато язык живой и типизированный.

Решение: **по первому реальному проекту**. Если первый — RimWorld, начинать с XML. Если Unity — с C#.

### 12.3 Какие маркеры первые

Бюджет встроенных — 10–15 (§14.7). Кандидаты в первую партию:

**Локальные (дёшево, без графа):**
- `large` — уже есть в рендере, формализовать как маркер.
- `stale` — уже есть для md-секций, расширить на docstring-и.
- `mutable-default`, `bare-except` — паттерны AST, простые.

**Глобальные (граф):**
- `hub` — есть данные, не оформлено как маркер.
- `cycle` — есть в `_find_cycles`, формализовать.
- `orphan` — новый, требует аккуратного определения (что значит «никто не ссылается» при динамических импортах).

**Композиции:**
- `large+hub` — high-risk изменения.
- `large+churn` — кандидат на декомпозицию.
- `stale+churn` — summary стоит обновлять приоритетно.

Остальные — после первой партии, по мере выявления полезности.

### 12.4 Миграция — порядок
**Порядок переставлен** относительно первой версии документа. Push — гипотеза (§3.2), а инфраструктура под гипотезу строится последней.

### Вертикальный срез (первое)

1. **Инкрементальный rebuild** — предусловие (§15.1). Без него всё остальное не имеет смысла.
2. **Per-patch diff из текущего манифеста** — не «модель как абстракция», а минимальный diff сигналов поверх существующего.
3. **3–4 hard-сигнала** — `api-change`, `new-cycle`, `xml-parent-missing`, `broken-ref`. Из §3.3.
4. **Прогон на реальных задачах** — лог реакции LLM. Какие сигналы вызвали действие, какие проигнорированы.

После среза — данные. Дальше по результатам.

### Если срез показал пользу

5. **История версий** — append-only, часть модели. Нужна для `signals(v_n) vs signals(v_{n+1})`.
6. **Query-тул** — заменить `get_index` / `survey_dir` / `list_files`.
7. **Файловый view (`files`)** — рабочий вид из INDEX_MODES (§6.2).
8. **Скоуп — `+` и `-`** — реализовать `.llmscope`.

### Позже

9. **Реестр маркеров, auto-discovery** — когда маркеров больше четырёх. На 3–4 это overhead.
10. **Композиции** — с 4-го маркера (§14.3).
11. **Адаптер XML (или C#)** — по первому реальному проекту.
12. **SCC, interface-impl, runtime-edge** — §16.5, по мере надобности.

**Инкрементальный rebuild — всегда первым.** Остальное переставляется.
### 12.5 Что осталось непроработанным
Требует обсуждения или измерения перед реализацией.

### Харнесс — как мерить пользу push

Гипотеза «LLM полезно реагирует на сигналы» (§3.2) проверяется не рассуждением. Дешёвый харнесс:

- **5–10 разных задач** на реальном проекте. Не только «понять, куда тратить усилия» — где символы могут быть не нужны. Ещё: «где реализовано X», «добавь фичу Y», «почини баг Z».
- **Каждая задача × режим.** Для push: с сигналами и без. Меряется число tool-вызовов, токенов, правильность результата.
- **Лог реакции LLM на каждый сигнал.** Что сделала в следующих N шагах: открыла указанный путь, поправила, проигнорировала. По этим данным видно, какие сигналы полезны, а какие — шум.

**Критерий успеха push:** уменьшение числа итераций чтения при сохранении правильности. Не «сигналы показались полезными» (самооценка LLM), а «задача решена с меньшим числом шагов».

### Что отложено

- **Churn и co-change — из git, не из своей истории.** `git log --name-only` даёт частоту изменений и co-change сразу. Своя история начинается с нуля и первые месяцы пуста. Свои версии модели нужны для `signals(v_n) vs signals(v_{n+1})`, а churn/co-change — внешний источник.
- **Инкрементальный граф** (§15.6) — метрики, не сводящиеся к счётчикам. `users`, `cycle`, `orphan`, `hub` считаются инкрементально. PageRank — если понадобится, отдельный дизайн.
- **Пресеты архитектур** (§14.8) — не решать до первого не-Python проекта.
- **Стоимость первого rebuild на 30k файлов.** 60–120 с (оценка, не замер). Нужен прогресс-бар или фоновая сборка.
- **Полный control-flow граф** — CodeQL/Joern, другой класс инструментов. Нам не нужен.
## 13. Что это даёт в итоге
<!-- summary: Одна модель вместо четырёх артефактов. Push-парадигма. История. Готовность к смешанным проектам. -->
Если гипотеза подтвердится:

- **Одна модель** вместо `INDEX.md` + `CODE_INDEX.md` + `CODE_INDEX_LUA.md` + манифестов + `survey_dir`.
- **Push-парадигма** — модель сигналит о hard-сломах (§3.3). Soft и hygiene — только если данные покажут пользу.
- **История** — diff между версиями. «Что изменилось, пока я не смотрела» — один запрос (§5).
- **Инкрементальность** — доли секунды на патч (§15, оценка).
- **Готовность к смешанным проектам** — адаптер на формат, не домен на формат (§8).
- **Один diff** для всего — структура, граф, метаданные в одном тексте (§4).

**Что подтверждено:** stale работает (наблюдение в сессиях). Инкрементальность — технически возможна. FS walk + манифест — работает в demo.

**Что гипотеза:** push для остальных сигналов. Реестр маркеров. Композиции. SCC и паттерны. Всё это проверяется вертикальным срезом (§12.4), не строением сразу.

Это не эволюция индекса. Это **смена парадигмы**: индекс — артефакт для чтения, становится анализатором с push-каналом. Но смена проверяется до того, как её закладывают в архитектуру.

Работа по частям. Сначала срез — 4 сигнала, лог реакции, данные. Потом решение про остальное.
## 14. Реестр маркеров
<!-- summary: Расширяемая система. Marker — чистая функция (snapshot, config) -> [Signal]. Snapshot — read-only. Rule — композиции над сигналами, отдельный слой. Auto-discovery из toolkit/markers/*.py. Стартовый текст — имена + одна строка; полное описание через query. -->

### 14.1 Зачем реестр

Маркеры меняются от проекта к проекту и от итерации к итерации. Если каждый маркер лезет в ядро — через 10 добавлений ядро покрыто 40 правками, половина из них устаревшая. Нужна расширяемость: новый маркер = новый файл, не правка ядра.

### 14.2 Три слоя

**Marker** — чистая функция. Вход `(snapshot, config)`, выход `Iterable[Signal]`. Никакого состояния. Легко тестировать.

```python
def marker(snapshot: Snapshot, config: dict) -> Iterable[Signal]:
    """LARGE: файл превышает порог размера.

    Значение: файл > 300 строк или > 16 KB.
    Параметры: threshold_lines (default 300), threshold_kb (default 16).
    """
    for f in snapshot.files():
        if f.lines > config.get("threshold_lines", 300):
            yield Signal(
                kind="large",
                path=f.path,
                severity="info",
                message=f"{f.lines} строк (порог {config['threshold_lines']})",
                data={"lines": f.lines},
            )
```

**Snapshot** — read-only view модели на версию. Не сама модель, а замороженная проекция.

Минимальный API:

- `snapshot.files(path="**")` — итератор файлов. Поля: `path`, `lines`, `size`, `ext`, `mtime`.
- `snapshot.units(path)` — unit'ы файла. `qualname`, `kind`, `line_start`, `line_end`, `head`, `body`.
- `snapshot.graph()` — граф. `edges()`, `callers(node)`, `callees(node)`, `users(path)`.
- `snapshot.signals(kind=None)` — **сигналы предыдущего запуска**. Нужны для маркеров, зависящих от истории.
- `snapshot.previous(path, field)` — значение поля в предыдущей версии.

Маркер **не может** изменить модель, получить полный снимок прошлой версии или добраться до внутренностей. Только через публичный API.

**Signal** — данные, не поведение.

```python
@dataclass(frozen=True)
class Signal:
    kind: str              # "large", "hub", "cycle"
    path: str              # где
    qualname: str | None   # если unit-уровень
    severity: str          # "info" | "warn" | "error"
    message: str           # человекочитаемое
    data: dict             # структурированные данные для композиции
```

`data` — то, что позволяет композиции работать без разбора message. Маркер `hub` кладёт `{"users": 36}`. Правило `hub+large` смотрит `signal.data["users"]`, а не парсит строку.

### 14.3 Композиции — отдельный слой

Не маркер, не правило внутри маркера. Отдельный модуль, читающий сигналы.

```python
def rule_large_hub(signals: list[Signal]) -> list[Signal]:
    """Large + hub = высокий риск изменений."""
    large_paths = {s.path for s in signals if s.kind == "large"}
    hub_paths = {s.path for s in signals if s.kind == "hub"}
    for path in large_paths & hub_paths:
        yield Signal(
            kind="risk-large-hub",
            path=path,
            severity="warn",
            message="Крупный и используется из многих мест — менять осторожно",
            data={},
        )
```

Правило **не знает** про модель. Только про сигналы. Тестируется на массиве сигналов. Композиции и маркеры развиваются независимо.

### 14.4 Auto-discovery

Реестр сканирует файлы в `toolkit/markers/*.py` (и `.patch_applier/markers/*.py` для пользовательских). Имя файла = имя маркера. Docstring → описание + параметры.

При старте сессии система собирает блок `## Маркеры` и добавляет в стартовый текст. Как `tools_schema.json`.

Формат в стартовом тексте:

```
## Маркеры

- large — файл или символ превышает порог размера
- hub — модуль используется из N+ мест
- cycle — модуль участвует в цикле импортов
- stale — summary секции устарел относительно тела
- orphan — символ или модуль, на который никто не ссылается
...

Полное описание: query(view="markers", name="large")
```

Полное описание через `query` — на случай, если LLM забыла, что даёт маркер, или он редко встречается.

### 14.5 Что показывать в стартовом тексте

Два уровня детализации:

- Полные описания — для маркеров, которые срабатывали в этом проекте (система знает из истории версий).
- Имя + одна строка — для остальных.

Это даёт полный реестр без раздувания стартового текста. Если маркеров станет 50 — стартовый текст не раздуется, потому что редкие будут однострочными.

### 14.6 Diff — уровень системы, не маркера

Маркеры **stateless**. Работают только с текущим снимком. Не знают про версии.

Diff сигналов — задача системы. Система сравнивает `signals(v_n)` и `signals(v_{n+1})`, находит разницу. Маркер говорит «есть сигналы X, Y, Z». Система говорит «в v_{n+1} появились A, B; в v_n их не было».

Это чище. Маркер не знает про diff, систему не волнует логика маркера.

### 14.7 Бюджет

**Реестр — не первый шаг.** Пока маркеров 3–4 (§12.4 срез), auto-discovery и `.patch_applier/markers/` — overhead. Выделять в систему стоит с 4-го маркера.

Когда реестр появится: жёсткий лимит на встроенные — 10–15. Остальное через `.patch_applier/markers/` по запросу. Иначе LLM не справится с реестром.

Композиции — тоже позже. `risk-large-hub` на 3 маркерах это `if large and hub`, не отдельный слой. Выделять стоит с 4-го.

### 14.8 Пресеты под архитектуру

Разные архитектуры требуют разных маркеров и разных порогов.

**Монолит:** `large` с порогом 1000 строк, нет `hub` (все файлы связаны), `cycle` не важен.

**Микросервисы:** `large` с порогом 200, `hub` — критично, `cycle` — критично, `cross-service-call` — новый маркер.

**RimWorld-мод:** `large` с порогом 500, `xml-orphan` (Def без ссылок), `xml-parent-missing` (Def ссылается на несуществующий ParentName).

Пресет — предустановленный набор параметров + включённых маркеров. Пользователь выбирает один. LLM может переопределить параметры через `set_scope`-подобный тул.

Пресеты — открытый вопрос. Не решать до первого не-Python проекта (RimWorld, Unity).

## 15. Инкрементальная модель
<!-- summary: На патч обновляются только изменённые файлы и их графовая окрестность. Кеш снимка, кеш сигналов. Локальные маркеры — по изменённым, глобальные — по окрестности. -->

### 15.1 Предусловие

Без инкрементального rebuild вся модель не имеет смысла. Полный rebuild 30k файлов — 60–120 секунд. На каждый патч это неприемлемо.

Инкрементальность — не оптимизация. Это **условие работоспособности**. Поэтому первый шаг миграции (§12.5).

### 15.2 Что обновляется на патч

Патч затронул файлы `{a.py, b.py}`. Что перестраивается:

1. **Структурный слой для `a.py`, `b.py`** — полный перепарсинг (файлы изменились).
2. **Графовый слой — локально.** Не «перестроить весь граф», а «обновить рёбра `a.py` и `b.py`, пересчитать `users` для затронутых узлов».
3. **Метаданные для `a.py`, `b.py`** — новые хэши, mtime, stale-флаги.
4. **Сигналы для `a.py`, `b.py`** — маркеры запускаются заново.
5. **Сигналы для соседей** — файлы, у которых изменилось графовое окружение (новый caller, новый цикл). Для них графовые маркеры пересчитываются, хотя сами файлы не менялись.

Не трогается: 29 995 остальных файлов. Их структурный слой, графовые рёбра, метаданные, сигналы — те же, что в v_n.

### 15.3 Кеш снимка

`snapshot.files()` — ленивая материализация. Первый маркер, обратившийся к нему, получает список. Все остальные — тот же объект.

Передача снимка 40 маркерам — 40 раз передать указатель. Микросекунды. Копий нет.

### 15.4 Кеш сигналов по файлу

`signals(v_n, file=foo.py)` — список. Если `foo.py` не менялся и его соседи не менялись, `signals(v_{n+1}, file=foo.py) = signals(v_n, file=foo.py)`.

Diff между версиями — сравнение кешированных наборов, не пересчёт.

Механика: каждый файл имеет `source_hash`. Если хэш совпадает и графовое окружение не изменилось — сигналы не пересчитываются.

### 15.5 Классы маркеров

**Локальные** — работают с одним файлом. `large`, `stale`, `mutable-default`, `bare-except`. O(1) на файл. При инкрементальном rebuild — только по изменённым.

**Глобальные** — работают с графом или историей. `hub`, `cycle`, `orphan`, `co-change`, `churn`. Дороже. При инкрементальном rebuild — только по затронутой окрестности.

Глобальные маркеры **объявляют**, что им нужно (`files` / `units` / `graph` / `history`). Если граф не менялся — глобальные маркеры не запускаются.

### 15.6 Инкрементальный граф

Обновление графа — самая сложная часть. PageRank в Aider не инкрементальный: пересчитывает при каждом commit. Нам это не подходит.

Для наших метрик (hub, cycle, users) инкрементальность проще, чем для PageRank:

- **users(node)** — счётчик обратных рёбер. Добавилось ребро → `users(target) += 1`. Убралось → `-= 1`. O(1).
- **cycle** — при добавлении ребра `a → b` проверить, есть ли путь `b → … → a`. Локальный DFS от `b`. Не «перестроить все циклы», а «проверить новый цикл через это ребро».
- **orphan** — при изменении рёбер обновить статус узлов, у которых изменился `users`.
- **hub** — порог по `users`. Если `users(node)` пересёк порог — сигнал.

PageRank, если понадобится, требует более сложной инкрементальной аппроксимации. Но для наших целей (hubs, cycles) не нужен.

### 15.7 Бюджет на маркер

Если маркер работает больше N миллисекунд на файл — система пишет предупреждение в лог. Чтобы «случайно тяжёлый» маркер не тормозил инкрементальный rebuild молча.

N — конфигурируемо, дефолт 50 мс.

### 15.8 Ожидаемые числа (оценка)

**Это прикидка, не замер.** Прогнать на реальном проекте, прежде чем закладываться.

На 30k файлов:

| Операция | Полный rebuild | Инкрементальный |
|---|---|---|
| Парсинг файлов | 60–120 с | 0,05–0,5 с |
| Построение графа | 20–30 с | 0,1–0,5 с |
| Прогон маркеров | 3–5 с | 0,05–0,2 с |
| Diff двух версий | 1–2 с | 0,01–0,1 с |
| **Итого на патч** | — | **~0,2–1 с** |

Маркеры — самая дешёвая часть. Узкое место — парсинг и граф. Инкрементальность снимает его.

### 15.9 Что это значит для дизайна

Четыре вещи, без которых модель на 30k файлов работает секундами:

- **Snapshot кеширует материализацию.** Один список на все маркеры.
- **Маркер объявляет, что ему нужно.** Локальные и глобальные разделены.
- **Сигналы кешируются по файлу.** Не пересчитываются без изменения.
- **Бюджет на маркер.** Защита от случайно тяжёлого.

С ними — доли секунды на патч.
## 16. Возможности анализа графа
<!-- summary: Что можно вычислить из графового слоя — компоненты связности, community detection, метрики Ca/Ce/I, hub, косвенные связи через интерфейс, рантайм-связи через DI. Разграничение «факт» vs «потенциальная связь». -->

Графовый слой — не только `users` и `cycle`. На нём можно считать стандартный структурный анализ. Это не новая архитектура, а **новые маркеры** над существующими слоями.

### 16.1 Прямые связи — что есть

Граф строится из `import`, `require`, `call`. Прямое ребро `A → B` означает: код в `A` явно ссылается на `B`. Факт из AST.

На прямых связях считаются:

**Компоненты связности (connected components).** Разбивает граф на изолированные подсистемы. Если граф зависимостей несвязный, каждая компонента — независимая группа модулей. Главная компонента — ядро приложения; маленькие — изолированные утилиты или мёртвый код.

Отвечает на вопрос «есть ли набор скриптов, связанных только между собой». Да — это компонента связности.

**Community detection (Louvain).** Если граф связный, но внутри него плотные кластеры — Louvain находит разбиение, максимизирующее модулярность: внутри групп связей много, между группами — мало. Это и есть «сильная связь внутри, слабая между».

Сложность — O(V log V), библиотека на ~200 строк. Применимо, когда компонента одна, но внутри неё структура.

**Метрики связности (Роберт Мартин):**

- **Ca (Afferent Coupling)** — сколько модулей зависят от этого. У нас уже есть как `→ N users`.
- **Ce (Efferent Coupling)** — от скольких зависит он.
- **I (Instability = Ce / (Ce + Ca))** — 0 (стабильный, фундамент) → 1 (нестабильный, лист).

`I < 0.2` + `Ca > 10` — фундамент, менять осторожно. `I > 0.8` — лист, менять безопасно.

### 16.2 Косвенные связи

Три типа, все вычислимы.

**Транзитивные зависимости.** `A → B → C` — `A` косвенно зависит от `C`. Считается обходом графа (BFS). Основа для blast radius: изменение в `C` затронет `A`, даже если `A` не импортирует `C` напрямую.

**Общие зависимости.** `A` и `B` оба зависят от `C`, но не связаны напрямую. Скрытая связь через общего предка. Если `C` меняется — оба под угрозой.

**Co-change.** Пара файлов, которые **изменяются вместе**, но не имеют структурного ребра. Индустрия называет это «hidden coupling» — файлы, разделяющие доменное понятие, но живущие в разных слоях. Требует истории версий (§5). Как только история появится — co-change становится доступным.

### 16.3 Связь через интерфейс — факт

Класс `B` реализует интерфейс `I` — **факт из AST**. Детектируется точно для C#, Java, Python (через `ABC` / `Protocol`), TypeScript.

Это создаёт **два ребра**: `A → I` (зависимость от абстракции) и `I ← B` (реализация). Формально `A` не знает о `B`, но в рантайме может быть вызван именно `B`.

**Почему этого достаточно.** Даже без анализа контейнера DI, зная, что `B` реализует `I`, а `A` зависит от `I`, можно утверждать: «`B` — **потенциальный** вызываемый `A`». Не гарантия, но сильный сигнал. Для LLM этого хватает, чтобы понять контекст при правке `B`.

**Паттерны детектируются по структурному отпечатку.** Паттерн «Стратегия» — это `A → I` + `I ← B, C, D` + делегирование в `A`. Все три признака — факты из AST. Тот же подход для «Фабрики» (`I ← B`, `Factory → I` + `new B()`), «Наблюдателя» (`I ← B`, `A → I` + список `[I]`). Это не ML, а эвристики на структуре.

### 16.4 Рантайм-связи — потенциальные рёбра

Связывание через DI-контейнер, фабрику, рефлексию переносит выбор реализации из компайл-тайма в рантайм. Статически граф `OrderService → SqlOrderRepository` отсутствует — есть только `OrderService → IOrderRepository` и `IOrderRepository ← SqlOrderRepository`.

**Но** большинство DI-регистраций статичны в коде. `services.AddScoped<IOrderRepository, SqlOrderRepository>()` — это **текст в файле**, который парсится. Из него строится дополнительное ребро `runtime-edge`.

Что даёт: «граф де-факто» — зависимости, как они существуют в реальности, а не только на бумаге. Для мёртвого кода, blast radius, community detection это важнее формального графа.

**Ограничения.** Если регистрация идёт через `Activator.CreateInstance` по имени из конфига — не видно. Если выбор стратегии по строке — не видно. Это не отменяет структурного факта (§16.3), но рантайм-ребро не строится.

### 16.5 Маркеры, которые это реализуют
Все — надстройки над §14. Не требуют новой архитектуры. **Это меню, а не план** — какие из них полезны, решает вертикальный срез (§3.2).

### Сильно связные компоненты (SCC) вместо community detection

**Louvain не подходит.** Даёт безымянные разбиения, нестабильные между версиями (без фиксированного seed). Кластер в diff начнёт шуметь — сегодня `discounts`, завтра `pricing`, а код не менялся. Противоречит принципу «каждый сигнал детерминирован» (§14.6).

**SCC — детерминированы и объяснимы.** Компонента сильной связности — это группа узлов, где каждый достижим из каждого. В коде это означает цикл импортов, и «меняются только вместе» становится фактом из графа, а не эвристикой.

Что даёт SCC:

- **Блок «меняется вместе»** — если правка в одном узле требует правки в другом, они в одной SCC.
- **Конденсация в DAG.** Сжатие каждой SCC в один узел даёт DAG — иерархию слоёв. «Нижние» слои (фундамент) и «верхние» (приложение) видны без параметров.
- **Граница блока как контракт.** Для SCC или каталога — какие символы используются снаружи. Если правка внутри блока не трогает внешне используемые символы — радиус мал, это локальное изменение. Это полезнее, чем просто членство в кластере.

Метрики Мартина (`Ca`, `Ce`, `I`) — про пакеты, не про файлы. Для файлов пороги `I < 0.2`, `Ca > 10` условны. Оставить как данные, не как маркеры по умолчанию. `hub` (уже есть) и `users` покрывают большую часть пользы.

**На компонентах:**

- `isolated` — модуль в маленькой компоненте связности (не в главной). Кандидат на «отдельная система» или мёртвый код.
- `scc-member` — модуль в сильно связной компоненте (цикл импортов).
- `scc-boundary` — символ внутри SCC, используемый снаружи. Контракт блока.

**На интерфейсах и паттернах:**

- `interface-impl` — `B` реализует `I`. Ребро `I ← B`. **Факт.**
- `interface-dep` — `A` содержит поле / параметр типа `I`. Ребро `A → I`. **Факт.**
- `strategy-pattern` — эвристика по совокупности `A → I` + `I ← B, C, D` + делегирование в `A`. **Эвристика**, не факт.

**На рантайм-связях:**

- `di-registered` — тип зарегистрирован в DI-контейнере. **Факт** (из текста регистрации).
- `di-consumer` — класс получает `I` через конструктор. **Факт.**
- `runtime-edge` — комбинация: `di-registered` + `di-consumer` → предполагаемое ребро `A → B`. **Потенциальная связь.**

**На косвенных связях:**

- `transitive-risk` — модуль, от которого косвенно зависят > N модулей (через цепочки).
- `hidden-coupling` — co-change выше порога без структурного ребра. **Источник — git**, не своя история (§16.2).

### Разделение «факт / потенциальная связь»

Критично для доверия LLM:

- **Факт:** `interface-impl`, `interface-dep`, `di-registered`, `di-consumer`, `isolated`, `scc-member`. Из AST или текста, детерминировано.
- **Потенциальная связь:** `runtime-edge`, `strategy-pattern`, `hidden-coupling`. Выводится, не гарантируется.

Маркеры разных классов не смешивать в одном имени. LLM должна знать степень уверенности.
### 16.6 Что это даёт LLM

Diff при правке одной из стратегий:

```
~ Mods/MyMod/Scripts/PercentageDiscount.cs
    ● interface-impl: IDiscountStrategy          (факт)
    ○ runtime-edge: → OrderCalculator             (потенциальная связь)
    ● scc-member: pricing (3 files, cycle)
```

Символ `●` — факт, `○` — потенциальная связь. LLM видит степень уверенности сразу.

LLM видит не «файл изменился», а «изменилась реализация стратегии, которая используется в калькуляторе, внутри изолированного кластера». Это контекст, который сейчас LLM собирает вручную — читая `OrderCalculator`, ища `IDiscountStrategy`, проверяя регистрации. Теперь он приходит сразу.

Для RimWorld-сценария: `xml-parent-missing` (Def ссылается на несуществующий `ParentName`) — это та же связь через интерфейс, только в XML.

### 16.7 Что не покрывается

- **Динамическая типизация** (Python без аннотаций, JS без типов) — связь через интерфейс не видна, потому что интерфейс не объявлен явно. Работает только по графу вызовов.
- **Рефлексия и метапрограммирование** — `getattr`, `importlib`, `eval`. Не видно статически.
- **Внешние зависимости** (библиотеки, фреймворки) — если они не в проекте, рёбра обрываются на границе.
- **Динамическая регистрация DI** (по имени, из конфига) — часть рантайм-связей не строится.

Это не мешает анализу, но задаёт границы: модель работает на статически выраженных связях, не претендует на полную картину рантайма.

**Ложная полнота — главный риск.** Если в сигнале `→ 3 users`, LLM поверит, что вызывающих три. А `getattr`, `importlib`, DI через конфиг, строковые ключи, XML-ссылки — не попали. LLM будет проверять **меньше**, чем стоило бы без графа.

**Защита:** маркер `graph-incomplete` на файл или символ, если в нём есть динамические конструкции (рефлексия, `getattr`, строковые ключи). Тогда LLM знает: «граф показывает N, но есть динамика, проверь вручную». Ставится на основе AST-эвристики, не претендует на точность.

### 16.8 Что не делать

- **Не строить полный control-flow граф.** Это отдельный класс инструментов (CodeQL, Joern), требует порядок сложности выше и работает в других задачах (security-анализ). Нам нужен **структурный** граф, не поток управления.
- **Не делать community detection на больших графах без нужды.** Louvain O(V log V), но на 30k модулей это секунды. Инкрементально сложнее. Если кластеры не запрашиваются — не считать.
- **Не смешивать факты и потенциальные рёбра в одном маркере.** `interface-impl` — факт, `runtime-edge` — потенциальная связь. Они должны быть разными маркерами, чтобы LLM знала степень уверенности.
- **Не пытаться детектировать все паттерны GoF.** Реально полезны 3–4: Стратегия, Фабрика, Наблюдатель, Декоратор. Остальные — академический интерес.
