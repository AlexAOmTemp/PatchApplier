# MCPBridgeRules — правила работы с MCP-мостом

## 1. Об этом документе
<!-- summary: Дополнение к LLM_START. Появляется только в Roblox-режиме. Формат вызовов, работа с multi_edit / execute_luau / script_read, известные баги. -->
<!-- tags: roblox, bridge, addendum -->

Это **дополнение** к `LLM_START`. Появляется ниже, когда пользователь включил Roblox-режим.

**Что здесь:** работа с ручным мостом чат↔Studio — форматы нативных вызовов, поведение конкретных инструментов (`multi_edit`, `execute_luau`, `script_read`), известные баги и обходные пути.

**Что здесь нет:** правил Roblox-кода (см. `RobloxCodeRules.md`) и правил конкретного проекта.

**При конфликте с `LLM_START`** — приоритет у `LLM_START`.

**Главное правило.** Инструменты моста (`multi_edit`, `execute_luau`, `script_read`, `search_game_tree`, `insert_asset`, ...) — **запасной путь**, не основной. Сначала проверь, решается ли задача унифицированным инструментом утилиты (см. `LLM_START` §Действия): `read_file`, `read_unit`, `replace_unit`, `insert_block`, `grep`, `replace_between`, `insert_at_anchor` и т.д. Если да — используй унифицированный. Особенности моста (включая известные баги из §5) утилита обрабатывает сама.

Инструменты моста бери только для операций, которых **у утилиты нет**: работа со свойствами инстансов, генеративные тулы, специфические операции DataModel. Разделение схем: унифицированные — в `LLM_START`, нативные — в `tools_schema.json` (приложен в стартовом тексте ниже).

## 3. Правила вызовов
<!-- summary: Пути с/без game., параметры инструментов, обходные пути для свойств и инстансов, ограничения Luau на имена, приблизительность графа импортов, риск открытой вкладки Studio. -->
<!-- tags: bridge, rules -->

- **Размер патча.** Предпочитать единый блок с несколькими вызовами вместо набора мелких. Пользователь копирует и выполняет каждый патч вручную — единый блок копировать быстрее.
- **Выполнение патча.** Блоки выполняются последовательно. На каждый вызов `outputs.json` содержит ответ с подробностями и меткой `is_error`.
- **Пути с `game.`**: `multi_edit`, `execute_luau`, `script_read` (через `target_file`) — путь начинается с `game.` (`game.ServerScriptService.X`).
- **Пути без `game.`**: `search_game_tree`, `inspect_instance` — путь начинается сразу с сервиса (`Workspace.X`).
- **`script_read`**: обязательный параметр — `target_file`, не `path`.
- **`multi_edit`** редактирует только код скриптов через `old_string` / `new_string` (для нового файла `old_string=""`). Не умеет менять свойства инстансов и не принимает `instances` / `path`+`properties`.
- **Свойства и не-скриптовые инстансы.** Менять свойства (`Color`, `Visible`...) или создавать не-скриптовые инстансы (`Part`, `Frame`, `ScreenGui`) — только через **`execute_luau`**.
- **`file_path`** в `multi_edit` / `execute_luau` — путь к инстансу в живой сцене Studio, не путь к файлу на диске.
- **`generate_material`** только создаёт `MaterialVariant` и возвращает имя — не применяет его. Назначить `part.Material` / `MaterialVariant` — отдельным `execute_luau`.
- **Структура папок через `execute_luau`.** При создании иерархии инстансов важно указывать правильный `className` (например, `Folder`, а не `Script`), иначе дочерние скрипты не будут выполняться.
- **JSON-эскейпинг Lua.** В Lua-коде внутри JSON экранируй `"` как `\"`, либо используй одинарные кавычки в самом Lua-коде (`'text'`) — так надёжнее.
- **`script_read` vs `.Source`.** `execute_luau { code = "return game.X.Y.Source" }` читает актуальный `.Source` всегда. `script_read target_file: ...` читает editor buffer; расходится с `.Source`, если файл открыт и был изменён программно.
- **Имена с точкой/спецсимволом не адресуются dotted-путём.** В Luau идентификатор (имя инстанса) может содержать только `[A-Za-z0-9_]`; всё остальное (`.`, `-`, `@`, пробел) делает имя недоступным через `game.A.B.C`. Это ограничение языка, не моста. Точки-разделители в пути нормальны — проблема только в точке **внутри одного имени**. Типичный пример: Wally-пакеты в `_Index` (`lm-loleris_profilestore@1.0.3.profilestore` — не прочитать через `read_file`/`read_unit`). Обход — только через `inspect_instance` (там путь без `game.`) или чтение с диска.
- **Граф импортов в `CODE_INDEX_LUA.md` — приблизительный.** Маркеры `← N imp` / `→ N users` для Luau строятся по `require` на стороне Studio и не видят динамических загрузок (`require(variable)`) и внешних потребителей (другие place, плагины). Считай их оценкой снизу: если в графе 5 users — их не меньше 5, но может быть больше. В Python-индексе (`CODE_INDEX.md`) тот же маркер точен (строится из AST).
- **Открытая вкладка Studio затирает `.Source` при сохранении.** Если модуль открыт в редакторе Studio и пользователь сохраняет буфер (`Ctrl+S` или закрытие вкладки), весь буфер записывается в `.Source`, перезаписывая любые программные правки. Verify-after-write этого не ловит — конфликт выявляется позже. Правило: перед правкой Roblox-модуля попросить пользователя закрыть его вкладку; после правки — переоткрыть, если она была открыта.

## 4. Кэш скриптов
<!-- summary: Изменения не применились в Play — пересоздать скрипт через execute_luau. -->
<!-- tags: bridge, cache -->

Если изменения в `StarterPlayerScripts` или `StarterGui` не применяются в Play-режиме — не правь файл повторно. Используй `execute_luau`, чтобы полностью удалить старый скрипт и создать новый с тем же именем и кодом. Это единственный надёжный способ мгновенно сбросить кэш Lua в Studio.

## 5. Известные проблемы моста
<!-- summary: multi_edit врёт, script_read stale, script_grep stale, execute_luau ограничения, get_console_output шум. -->
<!-- tags: bridge, known-issues -->

- **`multi_edit` может вернуть `applied` и не изменить `.Source`.** Проявляется на больших/содержательных файлах, чаще с `replace_all: true`. Условия воспроизведения не установлены: пакет из 5 вызовов, цепочка из 4 edit, chained replace_all — всё это работает на пустых файлах, но ломается на реальных (наблюдалось на `Config_Classes`, `Config_ItemTemplates`). **Правило:** правки существующих файлов — через `execute_luau` + `string.gsub` по `.Source`. Создание новых файлов через `multi_edit` — работает стабильно.
- **После любого патча проверять `.Source`.** `multi_edit` может отчитаться `applied`, но фактически ничего не записать. Дешевле проверить, чем отлаживать систему с частично применённым патчем.
- **`script_read` не читает editor-buffer.** Показывает старое состояние, если файл был изменён программно. Для автогенерируемых файлов (`CodeIndex`, миграции) читать через `execute_luau` + `.Source`.
- **`script_grep` показывает stale snapshot** после правок в текущей сессии. Результатам не доверять до перезапуска Studio.
- **`execute_luau` — золотой стандарт** для чтения и правки `.Source`, но имеет границы: не работает в Play Mode (`Target is not reachable`), запускается в изолированной Lua VM (свой `require` = новая копия модуля, не игровой инстанс), не умеет создавать `ModuleScript` в DataModel (sandbox-ограничение по capabilities — работает только создание `Folder` и не-скриптовых инстансов).
- **`get_console_output` может вернуть логи Studio/плагина, не игры.** Буфер 10 KB с отбрасыванием новых сообщений — при интенсивной загрузке последние важные строки пропадают. Для важного — писать явные `print` с маркерами.
- **`insert_asset`, `screen_capture`, `user_keyboard_input`** — проблемные, не использовать без явной необходимости. `screen_capture` в Play Mode игнорирует UI (`BillboardGui`, `ProximityPrompt`).
