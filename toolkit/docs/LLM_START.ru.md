# Patch Applier — стартовая инструкция для LLM

## 1. Что это и зачем
<!-- summary: Patch Applier — утилита правки проекта через JSON-патчи; четыре источника (Docs, Python, Luau-код, Roblox-сцена); ось MCP/Rojo для Luau-кода; индекс как карта, структурные единицы, детерминированный результат. -->
<!-- tags: overview, purpose -->

**Patch Applier** — утилита, которая позволяет LLM работать с проектом через **JSON-патчи**: один ответ LLM = список действий, каждое — чтение или правка. Патч применяется к четырём источникам: **Docs** и **Python** — на диске; **Luau-код** — на диске (Rojo-mode) либо в Studio (MCP-mode); **Roblox-сцена** (Parts, GUI, Folders) — всегда в Studio через MCP-мост. Режим Luau выбирает пользователь, он фиксирован в статусе строкой `luau:`.

**Ось: где живёт Luau-код.** Два взаимоисключающих режима:

- **MCP-mode** (`luau: mcp`) — код в Studio, `.Source` инстансов; путь вида `Service.X.Y`; правки через мост.
- **Rojo-mode** (`luau: rojo`) — источник истины `.luau` на диске; путь обычный файловый; правки — через те же AST-тулы, что и Python. Копия кода в Studio существует, но **зеркалит диск** и не является источником истины.

**`MCP` ≠ `Roblox`.** MCP — транспорт к DataModel Studio. Roblox-путь `Service.X.Y` — признак MCP-mode. Сцена (Parts, GUI, Folders) в обоих режимах идёт через MCP — это ортогонально режиму Luau-кода. Docs и Python — всегда на диске, режим их не касается.

Три несущих идеи:

1. **Индекс как карта.** `INDEX.md` (документы), `CODE_INDEX.md` (Python), `CODE_INDEX_LUA.md` (Luau) перечисляют все файлы, их секции/символы, размер, line-range, summary и граф импортов. По индексу ты решаешь, что читать, не открывая весь проект. Маркеры (`◉`, `← N imp`, `→ N users`, `⚠ large`, `⚠ cycle`, `[tests/]`, `[vendor/]`) — факты о файле; см. §10. Индекс пересобирается после каждого патча, меняющего структуру.

2. **Unit-модель вместо текста и номеров строк.** Правка адресуется unit'ом (unit целиком, или его часть `head`/`annotation`/`body`), либо блоком внутри body. Модель одинакова для `.py`, `.lua`, `.md`. Текстовые тулы (`replace_in_file`, `replace_between`) — только для того, что модель не адресует (комментарии, отдельные строки). Не по строке `N`, не по подстроке в тексте. Это устраняет падения из-за пробелов, эскейпов и сдвига номеров.

3. **Детерминированный результат.** После патча ты видишь структурный `Result` (delta, error_code, `##RESULT`) и diff индекса — «что применилось и что изменилось» без второго запроса на чтение.

Подробнее о требованиях — `docs/REQUIREMENTS.md`. Внутреннее устройство — `docs/ARCHITECTURE.md`.

**Что приходит в стартовом сообщении.** В самом низу этого стартового текста приложен первый снимок `get_status` — активный backend, версии индексов, политика по каталогам, флаг `run_python`. Читай его первым: он говорит, что доступно в этой сессии, до того как ты потратишь запрос. В любой момент можно запросить статус заново действием `get_status`.

**Этот документ — часть утилиты, не проекта.** LLM_START живёт в дереве toolkit (`toolkit/docs/`), не перечисляется в `INDEX.md` проекта и не правится обычными патчами. Если нужно изменить сам стартовый текст — это осознанное действие человека в репозитории утилиты, а не побочный эффект рабочего патча. По расширению — `.ru.md` / `.en.md` — выбирается язык.

2. **`RobloxCodeRules.md` (опционально).** Появляется ниже, если пользователь включил Roblox-режим. Правила Roblox-кода: Edit vs Play, `script_read` vs `.Source`, constraints, UI-вёрстка, JSON-эскейпинг, прочие типовые ошибки.

**Приоритет.** Если правило из опционального дополнения противоречит правилу утилиты — **приоритет у утилиты**. Дополнения описывают **что** писать в патч (домен); утилита описывает **как** он применяется.

**Порядок чтения при включённом Roblox-режиме.** «Что это» → «Парадигма» (как строить патчи) → `RobloxCodeRules.md` → `MCPBridgeRules.md` → «Стратегии» и «Коды ошибок» по мере необходимости.

**Если Roblox-режим не включён** — читаешь только этот документ; дополнений ниже не будет.

**Приоритет инструментов.** Всегда предпочитай **унифицированные инструменты утилиты** — unit-модель (`list_units`, `read_unit`, `replace_unit`, `insert_block`, `set_annotation`); граф и модульный поиск (`find_symbol`, `find_usages`, `symbol_graph`, `copy_unit`); текстовый escape hatch (`read_file`, `grep`, `replace_in_file`, `replace_between`, `insert_at_anchor`, `replace_range`); индексы и исполнение (`rebuild_index`, `rebuild_code_index`, `rebuild_lua_code_index`, `get_status`, `get_index`, `run_python`). Они покрыты path-политикой, логируются, проходят verify-after-write и **сами обрабатывают особенности backend'а** — включая известные проблемы моста: утилита прячет их внутри себя, тебе не нужно обходить их руками.

**Нативные инструменты MCP-моста** (`multi_edit`, `execute_luau`, `script_read`, `search_game_tree`, `insert_asset`, `generate_mesh`, `inspect_instance`, `http_get`, ...) — **только когда нет унифицированного инструмента** для нужной операции. Это относится к:

- работе со свойствами инстансов и DataModel напрямую (`execute_luau`);
- генеративным тулам (`generate_mesh`, `generate_material`, `segment_mesh`, `generate_texture`, `generate_procedural_model`);
- операциям без аналога в утилите (`search_asset`, `insert_asset`, `inspect_instance`, `http_get`, `list_roblox_studios`).

Если задача решается унифицированным тулом — **не переключайся** на нативный, даже если тот кажется проще. «Проще» здесь означает «без политики, без verify, без лога».

**Пример конфликта.** `MCPBridgeRules.md` §5 говорит: «правки существующих `Script.Source` делай через `execute_luau` + `string.gsub`». Это правило для **нативных** вызовов. Унифицированный `replace_unit` делает то же самое внутри себя — тебе не нужно писать gsub вручную. Приоритет у утилиты: используй `replace_unit`; `execute_luau`+gsub только если правишь произвольный фрагмент `.Source`, для которого нет структурного тула.

**Схемы разделены.** Схема унифицированных инструментов — таблицы в этом документе (§Действия, доступные тебе). Схема нативных — `tools_schema.json`, приложенная в стартовом тексте ниже, если пользователь включил `mcp.native_tools.enabled`. Если гейт выключен, вызов нативного инструмента вернёт `error_code="native_tools_disabled"` — это не ошибка, а гейт.

## 4. Первые шаги в новой сессии

**1. Проверь статус проекта.**

В стартовом сообщении пользователя обычно уже приложен вывод `get_status` — он формируется кнопкой «Стартовый текст» в GUI. **Снимок описывает конфигурацию сессии, не runtime.** Live-состояние моста в снимок не входит: LLM работает асинхронно (человек применяет патч через час или через день), и статус успел бы устареть. Если мост не поднят — патч упрётся в `backend_not_ready`, и LLM честно сообщит «Студия не подключена». Что в снимке важно:

- `backend` — `filesystem` / `mcp` / `composite`.
- `luau:` — **где живёт Luau-код**: `mcp` (Studio, `.Source`) или `rojo` (диск, `.luau`). Определяет формат путей и backend правок (см. §1).
- Список индексов с версиями `[vN]`.
- `## Policy Filesystem` — политика **только для файловых путей** (docs, Python, `.luau`-на-диске при Rojo).
- `## MCP` — политика DataModel Studio. К путям `Service.X.Y` FS-политика **не применяется**.
- Флаг `run_python`.

Если статуса в стартовом сообщении нет — запроси сам:

```json
[{"id": 1, "action": "get_status", "arguments": {}}]
```

**Флаги политики.** В блоке `## Policy Filesystem` у каждого пути стоит список флагов: `R` = read, `W` = write, `I` = index. `[RW]` — можно читать и писать, но не индексировать; `[RWI]` — всё три; `[]` — запрещено всё. Операция блокируется (`■ blocked`), если её флага нет в списке для данного пути. Три словаря политики независимы: разрешение на чтение не влечёт разрешение на запись или индексацию. Путь в политике может быть объявлен, даже если каталога физически нет на диске — политика декларативна.

**2. Получи индекс:**

```json
[{"id": 1, "action": "get_index", "arguments": {"kind": ["docs", "code"]}}]
```

`kind` — `docs` / `code` / `lua` / список из них. **`kind` обязателен** — не запрашивай всё сразу, выбирай домен явно. Индекс возвращается целиком; `max_bytes` — опциональный потолок, если ответ окажется огромным.

Индекс — карта мира: файлы, секции, диапазоны строк, размеры, зависимости. По нему ты находишь, что и где читать. Не читай файлы целиком без нужды.

## 5. Формат патча

**У каждого действия обязателен `id`.** Любое значение — число, строка, `null`. Оно не проверяется по типу и служит только меткой: по нему ты сопоставляешь своё действие с ответом.

```json
[{"id": 1, "action": "read_file", "arguments": {"file_path": "a.py"}}]
[{"id": 2, "action": "replace_in_file", "arguments": {...}}]
[{"id": "fix-import", "action": "replace_unit", "arguments": {...}}]
```

**Формат — группы.** Каждое действие в своей `[...]`; группы идут подряд. Разделитель между группами (новая строка или запятая) не важен. Для одного действия это тоже применимо — просто одна группа.

**Один фенс на весь ответ.** Это правило без исключений. Весь ответ — **один** блок кода (или совсем без фенса), внутри которого все группы подряд. Свой фенс на каждую `[...]` рвёт патч на несколько документов на стороне пользователя — он копирует их поштучно и теряет часть действий.

**Проверка перед отправкой:** посчитай открытия блоков кода в своём ответе. Должно быть **ровно одно** — либо ноль, если пишешь без фенса.

**Одно действие — одна группа.** Никогда не сливай несколько действий в один массив. Группы дают независимость (см. ниже).

**Почему группы.** Каждая группа парсится независимо. Ошибка в одной группе (пропущенная запятая, скобка, незакрытая кавычка, забытый `id`) **не мешает остальным**: валидные действия применяются, а проблемная группа игнорируется и описывается в блоке `=== Compiler messages ===` после лога.

**Что показывает комплилятор.** Формат в точности как у компилятора — `line N, col M`: три вида сообщений.

| kind | когда | что делать |
|---|---|---|
| `syntax` | фрагмент не парсится как JSON | проверь запятые, скобки, экранирование кавычек на указанной строке и колонке |
| `missing_id` | валидный JSON-объект, но нет поля `id` | добавь `id` — любое уникальное значение |
| `duplicate_id` | два действия с одинаковым `id` | не ошибка: оба применились, но метка теперь неоднозначна |

Пример вывода:

```
[1] ✓ read_file toolkit/code/toolkit/__init__.py
[2] ✓ replace_in_file toolkit/code/toolkit/core/patchparse.py
[4] ✓ read_file toolkit/docs/DECISIONS.md

=== Compiler messages ===
  line 9, col 105      syntax: Expecting ',' delimiter
  line 15, col 3       missing_id: object has no 'id' field
  line 27, col 3       duplicate_id: id=4 already seen at line 21
```

**Результаты по каждому действию:** `✓ ok` / `✗ error` / `■ blocked` (политика/песочница) / `– skipped` (неизвестное действие или нет arguments). Префикс `[N]` — это твой `id`, а не позиция в патче. Если `id` не задан, парсер подставит позицию, но в новом формате это всегда ошибка `missing_id`.

**Маркер `##RESULT:{...}`** — структурная сводка. Формат:

```json
{"ok": N, "errors": N, "skipped": N, "failed": [<индексы>], "blocked": [<индексы>], "diagnostics": [...]}
```

`failed` и `blocked` — номера действий (нумерация с 1 в этом патче), которые завершились `error` / `blocked`. `diagnostics` появляется, только когда есть сообщения компилятора.

По построению `errors == len(failed)` — `errors` это счётчик, `failed` — список тех же индексов. Отдельного `blocked_count` нет. Префикс маркера — ровно `##RESULT:` (с двоеточием).


**Патч — ручная операция, объединяй действия.** Пользователь копирует текст патча, вставляет, нажимает «Выполнить». Пять мелких патчей = пять копипастов, один большой = один. Не смешивай **независимые** логические действия (чтение и запись без причины, разнородные правки), но объединяй **механически связанные**: несколько однотипных `replace_in_file` в одном файле, `rebuild_*` после write, чтение и правка одной сущности подряд. Если следующее действие **зависит от результата** предыдущего (read → нужно увидеть → write), разделяй на два патча.

**Проверяй diff индекса после write-патчей.** `rebuild_*` возвращает `+` добавленные, `~` изменённые, `-` удалённые единицы. `-N` — единственный тип изменения, который не должен случаться без намерения (write-тул не теряет соседей). Если видишь `-` на файлах или секциях, которые ты **не** собирался удалять — останови работу и разберись. Рядом с `-N` стоит `⚠`.

## 6. Парадигма: работа по структурным единицам

**Главное правило: правь файлы через структурные единицы, не через текст и не по номерам строк.**

Инструменты `replace_range` (по номерам строк) и `replace_in_file` (по тексту) существуют, но их использование **ненадёжно** и часто приводит к падениям патчей:

- **`replace_range`** — номера строк смещаются после любой предыдущей правки. Дополнительная защита — параметр `expected_first_line`: если текст на `start_line` не совпадает, патч падает с `content_mismatch`, и **файл не трогается**. Порядок `replace_range` в патче проверяется автоматически (`range_order` / `range_after_write` — см. §14): несколько диапазонов на один файл идут **снизу вверх** (`start_line` строго убывает), и все они — **до** любых других write-тулов на тот же файл. Если правило нарушено — нарушающее действие отклоняется с явным кодом, но предшествующие правки **применяются**.
- **`replace_in_file`** — падает на пробелах, отступах, невидимых символах; одна и та же строка может встречаться в нескольких местах, `occurrence` помогает, но не всегда. Отдельная беда — эскейпы: `\u0413` в JSON и символ `Г` в исходнике дают один и тот же текст, но `replace_in_file` матчит по **байтам файла**, а `\u0413` там нет.

Для **всех поддерживаемых форматов** (`.py`, `.lua`, `.luau`, `.md`) используй unit-модель: `read_unit` / `replace_unit` / `insert_block` / `set_annotation`. Адрес — `qualname` (единый ключ для всех форматов: `Foo.bar`, `3`, `Format`, `<module>`) или `title_match` (матчер по подстроке в заголовке секции). Части `head` / `annotation` / `body`; блоки внутри body — через `block`. Эти тулы сами пересчитывают позиции от AST или структуры документа и не зависят от предыдущих правок.

**Текстовый escape hatch** (`replace_between`, `replace_in_file`, `insert_at_anchor`, `replace_range`) — только для того, что unit-модель не адресует: комментарии между unit'ами, отдельные строки внутри statement'а, файлы без парсера, fenced-код внутри md.

**Текстовые тулы работают на любом источнике.** `replace_in_file`, `replace_range`, `replace_between`, `insert_at_anchor` не зависят от формата — они оперируют текстом, который `read_file` вернул (для Roblox-путей — `.Source`). На Roblox они применяются так же, как на `.md`/`.py`.

**Точное чтение → точная замена (`escape=perline` + `search_repr`).** `read_file` по умолчанию возвращает **per-line repr**: каждая строка — отдельный Python-литерал с номером (`45: 'def foo():   \n'`). Видно всё невидимое — `\n` vs `\r\n`, хвостовые пробелы, табы — и при этом есть номера строк. Копируй строку (или несколько подряд, если нужен многострочный `search`) в `replace_in_file` — тул распакует литерал через `ast.literal_eval` и сматчит **точные байты**.

Две оси `read_file`: `numbered` (дефолт `true` — префикс `N: `) и `escape` (`perline` дефолт / `blob` / `none`). `blob` — весь фрагмент одним литералом (удобно копировать многострочный `search`); `none` — сырой текст без escape (для чтения-понимания). `numbered=true` + `escape=blob` — ошибка. CRLF сохраняется: если файл был с `\r\n`, после правки он останется с `\r\n`.

**⚠ Формат пути зависит от режима Luau.** В MCP-mode (`luau: mcp`) Roblox-путь — dot-notation: `ReplicatedStorage.X.Y`, первый сегмент — имя сервиса. В Rojo-mode (`luau: rojo`) Luau-файлы адресуются файловым путём, как `.py`-модули (`src/ServerScriptService/Foo/init.luau`).

**⚠ Имена с точкой/спецсимволом (только MCP-mode).** В `luau: mcp` точка — **разделитель**. Если **имя одного инстанса** содержит `.`, `-`, `@` или пробел — такой путь не читается (`read_file`, `read_unit`, `file_exists`, `grep_mcp`). Это ограничение Luau (имя идентификатора = `[A-Za-z0-9_]`), не утилиты. Типичный пример — Wally-пакеты в `_Index`. Обход — `inspect_instance` или чтение с диска.

**⚠ Открытые вкладки Studio.** Если пользователь держит Roblox-модуль открытым в редакторе Studio, при сохранении из редактора (Ctrl+S или закрытие вкладки) буфер затирает `.Source`, включая правки LLM. Перед патчем Roblox-модуля **спроси пользователя, закрыта ли вкладка**; если открыта — попроси закрыть. После патча, если вкладка была открыта — попроси переоткрыть, чтобы синхронизировать буфер с `.Source`.

`replace_range` и `replace_in_file` оставь для случаев, когда структурного инструмента объективно нет: точечная правка внутри module-level top region Python-файла, экзотические форматы без парсера, замена ровно одной строки с гарантированно уникальным текстом.

## 7. Действия, доступные тебе

### Чтение

| Действие | Аргументы |
|---|---|
| `read_file` | `file_path` + одно из: `section_number` (`"4"`, `"4.1"`), `section_title` (подстрока), `start_line`+`end_line`; иначе весь файл. Опц. `numbered` (дефолт `true`), `escape` (дефолт `perline`), `max_bytes`. Legacy `raw` (`repr`/`text`/`numbered`) принимается |
| `file_stat` | `file_path` — размер и разбивка по секциям |
| `file_exists` | `file_path` |
| `list_files` | `directory`, опц. `show_size`. При >2000 файлов возвращает только счётчик и подсказку использовать `survey_dir` |
| `survey_dir` | `path` (каталог), опц. `ext` (расширение или список), `top` (дефолт 20). Read-only: агрегат «сколько файлов и каких расширений» плюс разбивка по подкаталогам первого уровня. Для **незнакомого проекта** — первый контакт: увидеть форму дерева, не открывая 30 000 путей |
| `grep` | `pattern` + (`paths`: список / `directory`+`file_glob`); опц. `regex` (дефолт `true`), `fixed_strings`, `ignore_case`, `word_boundary`, `before`, `after`, `max_results`, `exclude_glob`. **Только файловая система.** Roblox-путь → ошибка `wrong_domain`, используй `grep_mcp` |
| `grep_mcp` | `pattern` + `directory` (Roblox-путь: **модуль или каталог** — если это сам скрипт, он тоже проверяется); опц. `fixed_strings` (дефолт `false`), `ignore_case` (только с `fixed_strings=true`), `before`, `after`, `max_results` (дефолт 200). **Только Roblox.** Один `execute_luau` на весь поиск. Паттерн — **Lua patterns**, не Python regex: `%d`, `%w`, `%.`, `.-` (ленивый). Для `\d`, `\w`, `\b`, `|`, групп — используй `grep` по выгруженному, либо простой литерал |

**Поля `Result`.** `status` (`ok` / `error` / `skipped` / `blocked`), `message`, `delta` (для write-тулов, `None` для чтений), `verified` (`bool` для write-тулов с read-after-write, `None` иначе), `error_code`, `action`.

`read_file` без параметров читает файл целиком — только для маленьких. Для секции в многофайловом индексе используй `section_number` (номер надёжнее заголовка: заголовки могут повторяться).

**Про `grep`.** `paths` — список **файлов**, не каталогов; каталог в `paths` молча уходит в «пропущено файлов». Для рекурсии — `directory` + `file_glob`. По умолчанию `regex=true` — `pattern` трактуется как регулярное выражение. Для поиска литеральной подстроки передай `fixed_strings=true` (в этом режиме `regex` игнорируется). `word_boundary=true` ограничивает матч границами идентификатора (`[A-Za-z0-9_]` с обеих сторон, ASCII — как в Lua `%w`); `Multiplier` не захватит `getMultiplier`.

**`grep` ↔ `grep_replace` — симметрия.** `grep_replace` (FS) и `grep_replace_mcp` (Roblox) используют **тот же матчер** и те же match-опции, что и парные `grep` / `grep_mcp`: `pattern`, `regex`, `fixed_strings`, `ignore_case`, `word_boundary`. **Что нашёл `grep` с данными параметрами — заменит `grep_replace` с теми же.** Это контракт, а не совпадение.

**Реконнессанс незнакомого корня.** Если корень проекта — чужой мир (игра, чужая кодовая база, архив), не начинай с `list_files` или `grep`. Сначала `survey_dir` по корню: получишь счётчики по расширениям и топ подкаталогов — форма дерева в 100 строк вместо 30 000. Дальше по ней решаешь, что важно, что в `.patchignore`, и уже точечно читаешь.

### Запись (текстовые тулы, escape hatch)

**Escape hatch для того, что unit-модель не адресует** — комментарии между unit'ами, отдельные строки внутри statement'а, файлы без парсера, fenced-код внутри md. Для всего, что адресуется unit'ом или блоком — используй unit-тулы (§Unit-операции).

| Действие | Аргументы |
|---|---|
| `replace_in_file` | `file_path`, `search`, `replace`, опц. `occurrence` (число или `"all"`), `search_repr` (дефолт `true`), `regex` (дефолт `false`) |
| `replace_range` | `file_path`, `start_line`, `end_line`, `new_content`, **настоятельно рекомендуется** `expected_first_line` |
| `replace_between` | `file_path`, `start_anchor`, `end_anchor`, `new_content`, опц. `include_start` (`true`), `include_end` (`true`), `occurrence` (`1`) |
| `insert_at_anchor` | `file_path`, `anchor`, `position` (`"before"` / `"after"`), `new_content`, опц. `occurrence` (`1`) |

**`occurrence`.** У `replace_in_file` — целое ≥1 (N-е вхождение) или `"all"`.

**`replace_in_file` — три tier'а матчинга.**

- **Tier 1 — byte-exact.** Как Ctrl+F: `search` содержит ровно те байты, что в файле. `foo()` — подстрока `foo()  `, найдётся; trailing сохранятся. Если матч есть — применяем молча.
- **Tier 2 — trailing-whitespace tolerance.** Если exact не нашёл — нормализуем trailing whitespace построчно в `search` и в файле, ищем. **Leading (indent) не трогаем** — она значима. Уникальный матч — применяем, message содержит пометку `(matched with trailing-whitespace normalisation; verify the line above)`. Несколько матчей — `bad_occurrence`, тот же механизм что и в Tier 1.
- **Tier 3 — no match.** Возвращаем `no_match` с `Searched: <repr>` и top-3 похожих строк из файла с маркерами невидимых: `␣` (trailing space), `⇥` (tab). По маркеру сразу видно, почему строка не нашлась.

**Regex-режим.** `regex: true` — `search` это Python-regex, `replace` поддерживает `\1`-backrefs. `occurrence` работает как в literal: `"all"` — все совпадения, число — N-е. Плохой паттерн → `bad_regex`. Полезно для «любой `def <name>():`» без ручной работы с якорями.

 У `replace_between` / `insert_at_anchor` — целое ≥1.

**`replace_between`** — замена блока между двумя короткими уникальными якорями. `include_start` / `include_end` определяют, съедаются ли сами якоря. Основной текстовый тул для многострочных замен. Якоря — короткие фразы без эмодзи.

**`insert_at_anchor`** — вставка текста перед или после уникального якоря, без замены.

**`replace_in_file`** для точных замен — 2–3 строки контекста, одной мало. **`search` копируй из вывода `read_file`, а не набирай вручную** — так не будет промахов по пробелам и эскейпам.

**`expected_first_line`** в `replace_range` — сверка первой строки диапазона. Не совпало → `content_mismatch`, файл не тронут.

**`replace_range` и `replace_in_file` — не надёжны.** Использовать только когда структурного тула нет.

### Массовая замена по файлам (`grep_replace`)
<!-- summary: grep_replace — массовая замена по файловой системе, симметричная с grep. Общий матчер, двухпроходный гейт (no_matches как ok / too_many_replacements до записи), dry_run=true по умолчанию, per-file atomic write. Работает на docs, Python, Luau-на-диске (Rojo). Не путать с grep_replace_mcp. -->
<!-- tags: tools, bulk-replace, filesystem -->

**`grep_replace`** — find-and-replace по файловой системе: `.md`, `.py`, `.lua`, `.luau` (в Rojo-mode), любые текстовые файлы. Симметричен с `grep`: те же `paths` / `directory`+`file_glob` / `exclude_glob`, те же `regex`, `fixed_strings`, `ignore_case`, `word_boundary` (и тот же дефолт `regex=true`). **Что `grep` нашёл — то `grep_replace` заменит.**

**Контракт.** Ровно одно из `pattern` / `mappings`:

- `pattern` + `replacement` — одиночная замена (Python-regex или литерал при `fixed_strings=true`).
- `mappings` — массив `[{"from": "...", "to": "..."}]`. Все пары применяются **за один проход одновременно** (longest-first, без каскада). `mappings` требует `fixed_strings=true`; `ignore_case` с `mappings` не поддерживается.

**Двухпроходный гейт.** Pass 1 — счёт замен без записи. Если `total == 0` → `ok` с сообщением «Совпадений не найдено» (симметрия с `grep`, **не ошибка**). Если `total > max_replacements` (дефолт 1000) → `too_many_replacements`, **ничего не записано**. Pass 2 — запись, только при `dry_run=false`. Дефолт `dry_run=true`.

**Что происходит при записи.** Каждый файл проверяется по policy (`write`) независимо: `blocked` файлы попадают в отдельный список, остальные применяются. Отката нет: падение N-го файла на записи не откатывает 1..N-1 (у MCP-версии этой проблемы не существует — там атомарно по построению). Частичное состояние — сознательный компромисс.

**Стратегия.** Та же, что у `grep_replace_mcp`:

- **A (безопасный, два патча).** Сначала `grep` — посмотреть, где и сколько вхождений. Потом `grep_replace(..., dry_run=true)` — увидеть counts по файлам. Если совпало — `dry_run=false`.
- **B (быстрый, один патч).** Сразу `grep_replace(..., dry_run=false, max_replacements=N)`, где `N` — ожидаемое число замен. Если реально больше — тул откажется, ничего не записав.

**Ограничения.** Текстовая замена, без AST: комментарии и строковые литералы включаются в поиск по определению. Не различает `local X` от глобального `X`. Симметрия гарантируется **внутри** домена: FS-`grep` ↔ FS-`grep_replace`, MCP-`grep_mcp` ↔ MCP-`grep_replace_mcp`. Между доменами — разный язык паттернов (Python `re` vs Lua patterns), это нормально.

**Типичный use case.** Ренейм идентификатора по всему проекту: `grep_replace(pattern="getMultiplier", replacement="calcMul", fixed_strings=true, word_boundary=true)`. Или батч: `mappings=[{"from": "getNormalizedChances", "to": "computeChances"}, {"from": "getMultiplier", "to": "calcMul"}]`. Или массовая замена в документации: `grep_replace(pattern="квест", replacement="миссия", directory="docs", fixed_strings=true)`.

### Roblox: массовая замена через мост (`grep_replace_mcp`)
<!-- summary: grep_replace_mcp — массовая замена по .Source Roblox-скриптов через мост. Общий матчер с grep_mcp, двухпроходный гейт (no_matches / too_many_replacements до записи), стратегии A (два патча) / B (max_replacements). Не путать с replace_in_file. -->

**`grep_replace_mcp`** — find-and-replace по `.Source` Roblox-скриптов одним вызовом. Работает через мост; Source не покидает Studio. Матчер общий с `grep_mcp` — те же `pattern`, `fixed_strings`, `ignore_case`, `word_boundary`, тот же обход scope. **Что нашёл `grep_mcp` — найдёт и `grep_replace_mcp` с теми же параметрами.**

**Контракт.** Ровно одно из `pattern` / `mappings`:

- `pattern` + `replacement` — одиночная замена (Lua-паттерн или литерал при `fixed_strings=true`).
- `mappings` — массив `[{"from": "...", "to": "..."}]`. Все пары применяются **за один проход одновременно** (longest-first, без каскада). `mappings` требует `fixed_strings=true`; `ignore_case` с `mappings` не поддерживается.

**Двухпроходный гейт.** Pass 1 — счёт замен без записи. Если `total == 0` → `no_matches`, если `total > max_replacements` (дефолт 1000) → `too_many_replacements`. В обоих случаях **ни один `.Source` не тронут**. Pass 2 — запись, только при `dry_run=false`.

**Стратегия.**

- **A (безопасный, два патча).** Сначала `grep_mcp` — посмотреть, где и сколько вхождений. Потом `grep_replace_mcp(..., dry_run=true)` — увидеть counts по файлам. Если совпало — `dry_run=false`. Это норма для незнакомых случаев и широких scope.
- **B (быстрый, один патч).** Сразу `grep_replace_mcp(..., dry_run=false, max_replacements=N)`, где `N` — ожидаемое число замен. Если реально больше — тул откажется, ничего не записав. Для знакомых идентификаторов и узкого scope.

**Ограничения.** Текстовая замена, без AST: комментарии и строковые литералы включаются в поиск по определению (`include_comments` / `include_strings` не поддерживаются — отделить их без AST нельзя). Не различает `local X` от глобального `X`. Wally-пакеты в `_Index` защищены тем, что их имена с `.` / `-` / `@` не адресуются dotted-путём.

**Не путать с `replace_in_file`.** Тот — точная замена в одном файле, с `search_repr` и `occurrence`; работает и на `.Source`. `grep_replace_mcp` — массовый рефактор по дереву, с гейтом и общим матчером с `grep_mcp`.

### Unit-операции: единая модель для `.py` / `.lua` / `.md` (приоритетно)

**Модель.** Файл — дерево **unit'ов**. Unit — именованная сущность:

- **kind**: `module` / `function` / `method` / `class` / `section`.
- **адрес** (JSON): один ключ — `qualname`. Python/Lua: `{"qualname": "Foo.bar"}`. Markdown: `{"qualname": "3"}` для нумерованной секции, `{"qualname": "Format"}` для безномерной (qualname = весь заголовок). Модуль: `{"qualname": "<module>"}`. Плюс матчер `{"title_match": "Format"}` — подстрока в заголовке секции (не адрес, а поиск). Legacy-алиасы `section_number` → `qualname`, `section_title` → `title_match` принимаются, но в новых патчах не использовать.
- **три части**: `head` — объявление (`def f():`, `class C:`, `function f(x)`, `## 3.1 Title`); `annotation` — описание сразу после head (docstring `"""..."""`, `--[[ ]]` или `---` в Lua, `<!-- summary: ... -->` в md; может отсутствовать); `body` — тело после head и annotation.
- **blocks** — нумерованные элементы внутри body: statements в функции, методы/атрибуты в классе, подсекции в секции. `block=3`, диапазон `"1-10"`, список `[1,3,7]`.

**Декораторы (Python).** Голова функции/класса **включает** строки `@decorator`. Голова модуля — нет: декоратор первого def/class принадлежит его блоку. Асимметрия намеренная, см. MODEL.md §2.

**Модуль:** head до **первого** def/class/function; всё от него — body (глобал между классами — блок в body, не head).

**Модель работает одинаково для `.py`, `.lua`, `.luau`, `.md`.** Физическое расположение annotation (AST / комментарий / HTML) — забота тула. **Комментарии между unit'ами, отдельные строки, содержимое fenced-кода в md** — не адресуются, для них текстовые тулы ниже. Если unit без docstring — `part=annotation` вернёт пусто (не ошибка).

**`part`** — строка или список (`"head"`, `"head,annotation"`, `["head","body"]`), канонический порядок `head → annotation → body`. У секций markdown есть ещё `own_body` — тело без подсекций (вид на `body`, не четвёртая часть): для секции с `###`-детьми это её собственный текст до первой подсекции; для функции и модуля совпадает с `body`. **`block`** — только в body (`not_applicable` иначе). `part` и `block` вместе не используются. При неоднозначности — `occurrence=N` (иначе `ambiguous_symbol`).

| Действие | Аргументы |
|---|---|
| `list_units` | `file_path` — карта unit'ов: qualname + kind + L-range + число блоков |
| `read_unit` | `file_path`, `address` (JSON); опц. `part`, `block`. Текст. Диапазон блоков — с метками `=== block N ===` |
| `replace_unit` | `file_path`, `address`, `new_text`, **ровно одно из `part` / `block`** (нет дефолта — иначе `scope_required`). `part="all"` — заменить целиком; `part="body"` — только тело, head и annotation сохраняются; `part="own_body"` — тело без подсекций. `block` (число / `"1-4"` / список) — блоки в body. **Пустой `new_text` — удаление:** с `block` — этих блоков; с `part="all"` — unit'а целиком. С другими `part` — опустошение этой части in-place |
| `insert_block` | `file_path`, `address`, `new_text`, `position` (`start`/`end`/`before`/`after`); `anchor` — номер блока или qualname дочернего unit'а (обязателен для `before`/`after`) |
| `set_annotation` | `file_path`, `address`, `text` — заменить annotation. **Только если она уже есть** (иначе `no_annotation`). Форму выбирает тул |

**Write-тулы.** После записи текст **парсится повторно**; если новый текст ломает парсинг или теряет unit — `result_syntax_error` / `result_missing_symbol`, файл **не тронут**. Отступ первой строки и EOL (`\n` vs `\r\n`) сохраняются.

**Lua.** Blocks внутри функций **пока не нумеруются** (`blocks=0`, `replace_unit(block=...)` → `not_applicable`) — token-парсер не даёт statement-границ. Для правки тела — `replace_unit part="body"`. `insert_block position="end"` вставит перед `return M`, если он есть.

**Lua в обоих режимах.** Rojo-mode: путь — обычный файловый (`.luau`), расширение определяется как для `.py`. MCP-mode: путь — `Service.X.Y` без расширения, `.Source` — это Luau. Утилита распознаёт MCP-путь сама (через `is_mcp_path`); один адаптер (`adapter_lua`) для обоих режимов. `list_units` / `read_unit` работают одинаково.

### Граф и модульный поиск

| Действие | Аргументы |
|---|---|
| `find_symbol` | `query` (подстрока qualname или путь модуля); опц. `manifest_path` |
| `find_usages` | `query` (подстрока пути модуля); опц. `manifest_path`, `limit`, `local`. **Модульный**: `imports` / `used by` |
| `symbol_graph` | `qualname`; опц. `occurrence`, `depth` (`1`), `max_nodes` (`300`), `manifest_path`, `kind` (`code`/`lua`), `local`. BFS: callees вниз на `depth`, callers — 1 уровень вверх |
| `copy_unit` | `source_file`, `target_file`, `selector`, опц. `position`, `anchor`, `container`. Копирует unit без правки source |

`find_symbol`, `find_usages`, `symbol_graph` читают манифест (`rebuild_code_index`; для Lua — `kind="lua"`).

**`symbol_graph` — обход, не поиск.** `find_symbol` ищет по имени; `symbol_graph` идёт от известного символа по рёбрам. Граф эвристичен: `self.X`, локальные имена, `import X`, `from X import Y` резолвятся; `getattr`, `from X import *`, вызовы на локальных — в `unresolved`.

### Индексы

| Действие | Аргументы |
|---|---|
| `get_index` | `kind` (`docs`/`code`/`lua`/список) — **обязателен**; опц. `max_bytes` (без дефолта — по умолчанию возвращается индекс целиком) |
| `get_status` | опц. `sections` (`session`/`indexes`/`policy`) |
| `rebuild_index` | опц. `docs_dir`, `output`, `skip_files` |
| `rebuild_code_index` | опц. `code_dir`, `output`, `manifest_output`, `skip_files`, `skip_dirs` |
| `rebuild_lua_code_index` | требует MCP (Roblox) |

`rebuild_*` возвращают `[vN]` — версию индекса — и структурированный diff от того, что лежало на диске до rebuild.

**`⚠` в конце diff-строки** означает, что были **удаления** (`-N`). Удаления — единственный тип изменения, который write-тул не должен производить без намерения: добавить файл или изменить его — норма, удалить соседний unit — аномалия. Если видишь `⚠` — проверь, что удалённое действительно должно было исчезнуть, прежде чем идти дальше. В обычном rebuild (только `~` и `+`) `⚠` не появляется.

### Исполнение

| Действие | Аргументы |
|---|---|
| `run_python` | одно из `script` (путь `.py` внутри проекта) / `module` (dotted-name); опц. `args` (список строк), `cwd`, `timeout`, `max_bytes`, `env`. **⚠ `module=` = `python -m` = `__main__`:** импорт модуля с `if __name__ == "__main__":` запустит его. Инцидент: `module="toolkit.runner.gui.app"` поднял второй GUI и поломал мост. Для проверки синтаксиса без запуска — `verify_syntax` |
| `verify_syntax` | `paths` (список `.py` файлов или каталогов) или `directory`; компилирует через `compile(src, path, "exec")` без импорта и без побочных эффектов. Заменяет ad-hoc `run_python(script="manual/verify_syntax.py")`. Полезно перед коммитом, когда надо убедиться, что правки не сломали синтаксис |

### Native Roblox tools (если разрешены)

Если пользователь включил `mcp.native_tools.enabled` в конфиге, ты можешь вызывать нативные инструменты Roblox через тот же формат патча, под их оригинальными именами: `{"action": "insert_asset", "arguments": {"assetId": "..."}}`. Правила работы с нативными инструментами — в `MCPBridgeRules.md`, их схемы — в `tools_schema.json`. Оба подмешиваются в стартовый текст, если пользователь включил Roblox-режим чекбоксом в GUI. Если конфиг не разрешает — вернётся `error_code="native_tools_disabled"`; это не ошибка, а гейт.

Работает только если в конфиге `exec.enabled=true`. Ограничения: только `sys.executable`, только внутри проекта, жёсткий таймаут, лимит вывода. Это **не песочница** — исполнение произвольного Python внутри проекта.

**`run_python` не подчиняется `filter.read` / `filter.write`.** У него отдельный гейт — `exec.enabled`. Проверка `script` и `cwd` идёт не через `FilterSpec`, а через «внутри `project_dir`»: `script` должен быть `.py` внутри проекта, `cwd` — существующая директория внутри проекта. Поэтому тесты, пишущие во временные подкаталоги проекта, работают, даже если `write`-политика эти подкаталоги не разрешает.

## 8. Версии индекса и diff

<!-- summary: Монотонный счётчик версий на каждый индекс; после write патч триггерит пересборку по домену путей; три операциональных правила чтения diff (проверяй diff после каждого write, сверяй `[vN]` при неожиданном, `[без изменений]` ≠ «файлы не менялись»). -->

У каждого индекса один **сквозной счётчик версий**: `[v1]`, `[v2]`, ..., `[v42]`. Он растёт на каждом rebuild и никогда не сбрасывается. Счётчик виден в выводе `get_status`, `get_index` и `rebuild_*`.

В **GUI** индексы пересобираются автоматически после патча. Триггер — **успешно применённый write**: тул с `op="write"` и `Result.status="ok"`. Читающие тулы, индекс-тулы и пустой патч — не триггерят.

Что именно пересобирается, решает домен затронутых путей (по `path_args` тула):

- **docs** (`INDEX.md`) — путь с расширением `.md`.
- **code** (`CODE_INDEX.md`) — путь `.py`.
- **lua** (`CODE_INDEX_LUA.md`) — Luau-код. В MCP-mode: Roblox-путь (начинается с имени сервиса), требует живого моста. В Rojo-mode: файловый путь (`.luau` на диске), мост не требуется.

Write без объявленных `path_args` (например, `run_python`) трактуется как «мог тронуть что угодно» — триггерит все включённые домены. Нативные MCP-тулы: read-only whitelist не триггерит, всё остальное (включая `execute_luau`) — только lua.

Каждый домен включается отдельно (`index_docs` / `index_python` / `index_lua`). Прямо в выводе патча видишь `rebuild_index ... [v45, +2 ~1]` со свежим diff.

**Хеш символа в lua-индексе.** У каждого символа в `CODE_INDEX_LUA.md` есть хеш — `- qualname [kind] (Lx–Ly) H1234567`. Это хеш исходного фрагмента (сигнатура + тело). Нужен, чтобы diff видел правки, **не сдвигающие строки**: если тело функции изменилось на пару символов без изменения длины, L-диапазон прежний, но хеш другой → символ попадёт в diff как `~ qualname ... (изменён)`. В `CODE_INDEX.md` (Python) хеша символа нет — там diff работает по L-диапазону.

**Как читать diff.** Три правила, все операциональные:

1. **После каждого меняющего файлы патча проверяй diff индекса.** Он показывает реальные изменения в файлах — не намерения патча, не твою память, а что реально стало другим на диске. Если diff пуст (`[без изменений]`) — на диске ничего не поменялось.

2. **Если diff не тот, что ожидал — сверь `[vN]`.** У тебя в памяти последний `[vN]`, который ты видел. Если сейчас `[vN+K]` с K > 1 — между ними был пропущенный rebuild (автоматический warm-up при рестарте GUI, чужой rebuild), и он мог изменить что угодно. Малый разрыв (1–2) — доверяй diff'у. Большой или подозрительный — вызови `get_index` заново, не складывай diff'ы из памяти.

3. **`[без изменений]` ≠ «файлы не менялись».** Это значит «индекс на диске совпадает с тем, что было бы собрано сейчас». Пропущенный warm-up мог уже собрать индекс с новыми данными, и тогда следующий rebuild честно покажет `[без изменений]`, хотя между твоим прошлым чтением и сейчас файлы менялись. Проверка — по номеру версии: если `[vN]` вырос, а diff пуст, значит кто-то (warm-up, другой процесс) уже учёл эти изменения раньше.

## 9. Формат markdown-документов

Индекс парсит заголовки строго:

```
## N. Название              ← секция верхнего уровня
<!-- summary: одна строка -->  ← обязательно для ##
<!-- tags: a, b -->           ← опционально

тело

### N.M Название           ← подсекция
<!-- summary: ... -->        ← опционально
```

- Заголовки: `## N.`, `### N.M`, `#### N.M.K` (пробел после номера, точка только у `##`).
- `summary` — одна строка, без переносов.
- `tags` — через запятую, опционально.

## 10. Метки в индексе

Метки — **факты**, не суждения. Каждая выводится из AST, графа импортов или пути; интерпретацию («это хаб», «это мёртвый код») делает читатель.

**Документы (markdown).**

- `⚠ no summary` — у секции нет `<!-- summary -->`. Добавь через `set_annotation`.
- `⚠ stale` — тело секции менялось после последнего подтверждения summary. Метка применяется **только к секциям markdown** (`## N.`, `### N.M`). Прочитай секцию и обнови annotation через `set_annotation` (если описание устарело). Подтверждение без правки файла (аналог старого `verify_section`) в текущей модели не реализовано.
- `⚠ large` — листовая секция >16 KB. Разбей на подсекции `### N.M` или оставь как есть.

**Код (Python и Lua).** У модуля — суффикс в строке заголовка `## path  (N стр., M KB) <маркеры>`. У символа — суффикс после L-диапазона.

| Маркер | Уровень | Что значит |
|---|---|---|
| `◉` | модуль | есть `if __name__ == "__main__":`. Факт из AST. У Lua-модулей не бывает |
| `← N imp` | модуль | модуль импортирует N других модулей **внутри индекса**. Внешние импорты (stdlib, third-party) не считаются. Не показывается при N=0 |
| `→ N users (M tests)` | модуль | модуль импортируют N других модулей индекса; M из них — тесты (по пути `tests/`, `test_*`). Не показывается при N=0 |
| `[tests/]` | модуль | файл лежит в тестовой директории или назван `test_*` |
| `[vendor/]` | модуль | путь содержит `vendor/`, `_Index/` или `node_modules/` |
| `⚠ large` | модуль | > 300 строк или > 16 KB. Подсказка: не читай целиком, читай по секциям/символам |
| `⚠ large` | символ | определение длиннее 100 строк |
| `⚠ cycle` | модуль | участвует в цикле импортов внутри индекса |

**`→ N users` для Lua приблизительно.** Luau-граф строится по `require` и не видит динамических загрузок и внешних потребителей. В Python — точный (AST). В Lua — оценка снизу.

**Suppression.** В шапке файла (первые 20 строк) можно заглушить маркеры директивой:

```python
# pa: no-users, no-large
```

Имена: `main`, `imports`, `users`, `tests`, `vendor`, `large`, `cycle`. `all` глушит всё. Несколько строк мержатся. Директива — **факт про файл** (живёт с ним, версионируется), не настройка утилиты.

Зачем глушить: файл сам знает, что `# pa: no-large` (сгенерированные данные), или `# pa: no-users` (публичный API, внешние потребители не видны в индексе).

## 11. Стратегии

**Быстрый выбор тула.** От задачи к инструменту. Подробные сценарии — ниже.

| Задача | Тул |
|---|---|
| Прочитать секцию / файл | `read_file` / `read_unit` |
| Заменить тело функции | `replace_unit part="body"` |
| Заменить только «своё» тело секции | `replace_unit part="own_body"` |
| Удалить метод из класса | `replace_unit(block=N, new_text="")` |
| Удалить unit (функцию, секцию) | `replace_unit(part="all", new_text="")` |
| Вставить statement в функцию | `insert_block` |
| Найти unit по имени | `find_symbol` |
| Кто вызывает X | `symbol_graph qualname="X"` |
| Кто импортирует модуль | `find_usages query="path/to/mod"` |
| Заменить строку (точная / с trailing) | `replace_in_file` (tier 1 / tier 2) |
| Regex-замена | `replace_in_file regex=true` |
| Первый взгляд на незнакомый корень | `survey_dir` |
| Массовая замена в файлах (docs / Python / Luau-на-диске) | `grep_replace` |
| Массовая замена в Roblox-коде | `grep_replace_mcp` |
| Пересборка индекса после правки | `rebuild_*` (авто при write) |
| Запустить тест / скрипт | `run_python` |

**Понять механику X:**
**Понять механику X:**
1. `grep pattern="X"` по индексу — увидишь все секции по всем докам сразу.
2. `read_file section_number="N"` — точечно.
3. По ссылкам из прочитанного — куда идти дальше.

**Внести правку:**
1. `read_file section_number="N"` — прочитай секцию.
2. Если `⚠ stale` — перепиши annotation через `set_annotation` (если описание устарело). Подтверждение без правки файла (аналог старого `verify_section`) в текущей модели не реализовано.
3. Сформируй патч.
4. Проверь результат тем же `read_file`.

**Найти unit (символ / секцию):**
1. `list_units file_path=...` — карта файла: qualname + kind + line-range + число блоков.
2. `read_unit file_path=..., address={...}` — текст unit'а или его частей.
3. Для поиска по имени без файла — `find_symbol query="..."` (манифест).

**Прочитать unit частями:**
1. `part="head"` — сигнатура / заголовок.
2. `part="annotation"` — docstring / summary.
3. `part="body"` — тело.
4. `part="head,annotation"` или список — несколько частей.
5. `block="1-5"` — диапазон блоков в body.

**Править unit:**
1. `read_unit` — посмотреть текущее состояние.
2. `replace_unit` — заменить unit целиком (`part=all`) или только часть (`part="body"` — head и annotation сохраняются). Пустой `new_text` с `part="all"` — **удалить unit целиком**.
3. `replace_unit(block=N)` — заменить блок или диапазон блоков в body. Пустой `new_text` с `block` — **удалить блоки**.
4. `insert_block` — вставить блок в `start` / `end` / `before anchor` / `after anchor`.
5. `set_annotation` — заменить docstring / summary. **Только если annotation уже есть** — создание с нуля не поддержано.

**Навигация по графу:**
1. `find_symbol query="X"` — где определение X (имя → модуль).
2. `find_usages query="path/to/mod"` — модульный обход: кто меня импортирует (`used by`), кого импортирую я (`imports`).
3. `symbol_graph qualname="X" depth=2` — от известного символа: callees вниз, callers вверх. Граф эвристичен (см. §7).

**Граница символьного уровня.** Символьный reverse («где вызывается `X.foo`») реализован только для Python. Для Lua `symbol_graph kind="lua"` вернёт модуль символа без callees/callers — манифест Lua не содержит поля `calls`. Модульный reverse (`find_usages`) для Lua работает по `require` и приблизителен.

**Массовая правка по проекту:**
1. Файловая система — `grep` находит вхождения, `replace_in_file` с `occurrence="all"` правит все вхождения в одном файле.
2. Roblox — `grep_replace_mcp` одним вызовом (стратегии A / B из §7).

## 12. Что помнить

- **Один фенс на патч.** Не оборачивай каждую группу в свой блок кода — весь ответ идёт **одним** блоком (или совсем без него). Самая частая ошибка — «разорванный фенс». См. §5.
- **Не полагайся на память.** Если факт нужен для решения — перечитай.
- **`⚠ stale` ≠ «устарело».** Это «не проверено после правки». Обнови annotation через `set_annotation`, если описание устарело.
- **`blocked` ≠ `error`.** `blocked` — политика или песочница; не повторяй, сообщи пользователю.
- **Файлы >100 KB** — только секциями или через `max_bytes`. `read_file` без границ читает целиком — для большого файла это забивает контекст. Сначала посмотри размер в индексе (`⚠ large`, метрики в заголовке).
- **Перед правкой — прочитай актуальное состояние.** `read_unit` / `read_file` → потом `replace_*` / `insert_*` / `delete_*`. Индекс мог устареть, предыдущий патч мог не примениться, файл мог измениться. Исключение — идемпотентные операции вроде `create_file` для точно отсутствующего файла.
- **Патч — ручная операция.** Объединяй механически связанные действия (несколько правок в одном файле, `rebuild_*` после write). Разделяй, если следующее зависит от результата предыдущего (см. §5).
- **Проверяй diff от `rebuild_*`.** `-N` + `⚠` — аномалия, разбирайся до продолжения.
- **Скрытое = закрытое.** Пути из `.patchignore` в корне проекта (dotdir'ы, `__pycache__`, `node_modules`, `venv` по дефолту) закрыты для чтения/записи/индексации. Если нужен доступ — пользователь откроет через GUI. Скрытое в дереве — не «неважное», а «недоступное».

## 13. Коды ошибок

`Result` содержит `error_code` — машиночитаемую метку. Что делать:

**Парсинг патча:**
- Сообщения компилятора о проблемных группах приходят отдельным блоком `=== Compiler messages ===` после лога, плюс полем `diagnostics` в `##RESULT`. Три вида: `syntax` (фрагмент не парсится как JSON), `missing_id` (валидный объект без обязательного `id`), `duplicate_id` (два действия с одной меткой). Каждое сообщение несёт `line`, `column`, `message`. Остальные действия патча применяются нормально — проблемная группа просто игнорируется.

**Цель не найдена или неоднозначна:**
- `not_found` — unit / секция / файл не найдены. Проверь адрес, имя, номер. Убедись, что индекс актуален (`get_index`).
- `ambiguous_symbol` — адрес встречается N раз. Прочитай сообщение: там L-диапазоны каждого вхождения. Передай `occurrence=N` (N-й сверху вниз).
- `occurrence_out_of_range` — N вне диапазона; сообщение скажет, сколько вхождений.
- `block_out_of_range` — номер блока больше, чем есть в body (в сообщении — сколько блоков).
- `not_applicable` — операция над блоками применена к unit'у без блоков (Lua-функция без statement-границ, head/annotation вместо body).
- `no_annotation` — `set_annotation` вызван на unit'е без существующей annotation; создание с нуля не поддержано.
- `no_parts` — `replace_unit part=[...]` — ни одной из запрошенных частей нет у unit'а.
- `anchor_not_found` — не найден блок-якорь для `position=before|after` (номер блока или qualname дочернего unit'а).
- `no_match` — `replace_in_file`: `search` не найден.
- `kind_required` — `get_index`: `kind` не передан, а он обязателен.
- `unknown_kind` / `bad_kind` — `get_index`: невалидный `kind`.
- `unknown_section` — `get_status`: невалидный `sections`.

**Форма вызова:**
- `empty_input` — `new_text` / `new_code` / `new_body` / `new_content` пусты.
- `bad_position` — `position` не из `start|end|before|after`.
- `anchor_required` — `position=before|after` без `anchor`.
- `anchor_not_allowed` — `position=start|end` вместе с `anchor`.
- `bad_occurrence` — `occurrence` не целое.
- `bad_part` — `part` не из `all|head|annotation|body`.
- `bad_block` — строка `block` не разобралась (`block="abc"`).
- `bad_block_range` — `replace_unit(block=...)` получил несоседние блоки (`"1,3"`); допустим только непрерывный диапазон.
- `scope_required` — `replace_unit` без `part` и без `block`. Передай одно из двух.
- `scope_conflict` — `replace_unit` с `part` и `block` одновременно. Ровно одно.
- `range_order` — несколько `replace_range` на одном файле не по убыванию `start_line`. Правильный порядок — снизу вверх.
- `range_after_write` — `replace_range` идёт после другого write-тула на том же файле; его номера строк устарели. Поставь его раньше других write.
- `ambiguous_input` — `run_python`: оба из `script`/`module` или ни одного.

**Парсинг:**
- `syntax_error` — исходный файл не парсится. Файл не тронут.
- `result_syntax_error` — предлагаемое содержимое не парсится. Патч отменён, файл не тронут. Поправь `new_text` / `new_code`.
- `result_missing_symbol` / `result_missing_section` — после правки unit/секция исчезли из файла. Патч отменён, файл не тронут.

**Манифест (`find_symbol` / `find_usages` / `symbol_graph`):**
- `empty_query` — пустой `query`.
- `manifest_not_found` — файл манифеста не найден; запусти `rebuild_code_index`.
- `manifest_read_error` — не могу прочитать манифест.
- `manifest_invalid` — манифест не JSON или не список модулей.

**Политика и песочница (`status=blocked`, не retry):**
- `hidden_path` — путь скрыт через `.patchignore` или как dot-dir. Не открывается обычными тулами; пользователь может открыть через GUI.
- `filter` — путь запрещён per-path policy (read/write/index по `workspace.json`), либо корень не объявлен в workspace.
- `sandbox` — путь вне проекта.
- `backend_not_ready` — MCP (Roblox) ещё не поднялся или упал. Жди или нажми `↻` в GUI.
- `native_tools_disabled` — нативный MCP-тул вызван, но `mcp.native_tools.enabled=false` в конфиге. Не ошибка, а гейт.
- `exec_disabled` — `run_python` выключен в конфиге.
- `script_outside_project` / `cwd_outside_project` — пути `run_python` вне проекта.

**Исполнение:**
- `timeout` — скрипт убит по таймауту (сообщение содержит `TIMED_OUT`).
- `nonzero_exit` — код возврата ≠ 0; сообщение содержит `exit=N`.
- `script_not_python` / `script_not_found` — параметры `run_python`.

**Файловые операции:**
- `already_exists` — `create_file`: файл уже есть.
- `source_not_found` / `destination_exists` — `move_file` и `copy_file`.
- `backend_not_supported` — `copy_file`: backend не умеет `copy()` (например, MCP без clone-семантики для этого типа инстанса).

**`grep` / `grep_replace` (FS), `grep_mcp` / `grep_replace_mcp` (Roblox):**
- `wrong_domain` — путь не того домена. Для FS-тулов Roblox-путь → ошибка (используй `*_mcp`); для MCP-тулов файловый путь → ошибка (используй FS-версию).
- `empty_pattern` — `grep` / `grep_mcp`: `pattern` пустой.
- `bad_regex` — `grep` / `grep_replace` (FS): некорректный Python-regex в `pattern` при `regex=true, fixed_strings=false`.
- `bad_options` — `ignore_case` без `fixed_strings=true`; `max_replacements <= 0`; `ignore_case` вместе с `mappings`.
- `bad_input` — `grep_replace` / `grep_replace_mcp`: нужно ровно одно из `pattern` / `mappings`.
- `empty_mappings` / `patterns_in_mappings_not_supported` / `bad_mapping` / `empty_mapping` / `noop_mapping` / `duplicate_mapping` — форма `mappings`.
- `no_matches` — у FS `grep_replace` **не ошибка**: возвращается `ok` с сообщением «Совпадений не найдено» (симметрия с `grep`). У `grep_replace_mcp` — `error_code=no_matches`; ничего не записано.
- `too_many_replacements` — `grep_replace` / `grep_replace_mcp`: суммарных замен больше `max_replacements`. Ничего не записано. Сузь scope, добавь `word_boundary=true`, уточни `pattern` или подними лимит.
- `backend_not_supported` — backend не поддерживает `grep_mcp` / `grep_replace_mcp` (нужен MCP).

**Копирование структурных единиц:**
- `bad_selector` — `copy_unit`: `selector` не dict или содержит не ровно один ключ из `section_number` / `section_title` / `qualname`.
- `unknown_unit` — `copy_unit`: расширение `source_file` не `.md`/`.py`/`.lua`/`.luau`; либо секция не найдена в source.
- `wrong_selector` — `copy_unit`: ключ не соответствует расширению (`.md` + `qualname`, либо `.py`/`.lua` + `section_*`).
- `container_not_supported` — `copy_unit`: `container` передан для `.md` или Lua-файла.
- `no_format` — `rebuild_*` / `copy_unit`: `fmt=None` (неинициализированный `Format` в сессии).
- `result_parse_error` — `lua_copy_symbol`: новый target не парсится; файл не тронут.

**Нативные вызовы:**
- `native_error` — исключение внутри нативного тула MCP-моста (`execute_luau`, `multi_edit`, ...). Смотри `message` — там класс и текст исключения.
- `requires_mcp` — `rebuild_lua_code_index`: backend не умеет `execute()` (нет MCP).

## 14. Чего не делать

- **Не использовать `replace_in_file` для многострочных замен.** Даже 2–3 строки контекста легко промахиваются по пробелам, невидимым символам или эскейпам. Для блочных замен есть `replace_between` — два коротких якоря вместо длинного `search`.
- **Не использовать `replace_range` для правок в поддерживаемых форматах.** Для `.py` / `.lua` / `.md` всегда есть unit-тулы (`replace_unit`, `insert_block`, `set_annotation`) и `replace_between`. `replace_range` уместен только для module-level top region и файлов без парсера. Если всё же нужен — передавай `expected_first_line`.
- **`replace_range` на файл — только снизу вверх и до других write-тулов.** Правила проверяются автоматически в `Patcher.apply`:
  - **`range_after_write`** — `replace_range` идёт после другого write-тула (`replace_in_file`, `replace_unit`, `overwrite_file`, …) на том же файле; номера строк могли сместиться. Поставь `replace_range` **раньше** других write на этот файл.
  - **`range_order`** — несколько `replace_range` на одном файле не по убыванию `start_line`. Идут сверху вниз → нижний сдвиг ломает верхний. Правильно — **сначала нижние (большие `start_line`), потом верхние**.
  - Нарушающее действие отклоняется (`error_code` = `range_order` / `range_after_write`), но **предшествующие правки применяются**. Файл остаётся в предсказуемом состоянии: не «рандом», а «часть применена, часть отклонена с причиной».
- **Не путать `part` и `block`.** `part` — `head` / `annotation` / `body` (три части unit'а). `block` — нумерованный элемент **внутри** body. Вместе не используются: `part`+`block` в одном вызове → ошибка.
- **Не пытаться записать annotation там, где её нет.** `set_annotation` работает **только на замену существующей**. Если annotation отсутствует — `no_annotation`. Создание с нуля — через `replace_unit part="body"` (вставить руками) или `insert_block`.
- **Не использовать `replace_unit(block=...)` для разрывного диапазона.** `"1,3"` → `bad_block_range`. Только непрерывный (`"1-3"`). Разрывные — несколькими вызовами.
- **Не складывать diff'ы из памяти.** Если разрыв версий больше 1–2 — перечитай `get_index`.
- **Не строить цепочки вызовов через серию `read_unit`.** Если нужно «кто зовёт X» или «что зовёт X» — `symbol_graph qualname="X"` одним вызовом.
- **Не игнорировать `⚠ stale`.** Перед правкой секции — актуализируй annotation через `set_annotation`.
- **Не retry `blocked`.** `■ blocked` — решение политики (в т.ч. `.patchignore`), а не transient-ошибка.
- **Не пытаться чинить синтаксис через `replace_unit`.** Если файл не парсится — `syntax_error`; читай его как текст (`read_file`).
- **Не гадать.** Если `not_found` или `ambiguous_symbol` — прочитай индекс, unit или секцию, не угадывай адрес.

## 15. С чего начать

1. Прочитай статус — обычно он приложен в конце стартового текста; если нет — запроси `get_status`.
2. `get_index` — увидеть карту.
3. Читать секцию → править секцию → проверять.
4. Если что-то неясно — спроси пользователя, не гадай.

## 16. Примеры патчей

**Один пример = один патч = один фенс.** Все группы примера идут в одном блоке кода (см. §5). Действия внутри примера выполняются по порядку.

Все примеры ниже — с обязательным `id`. Одно действие — одна `[...]` группа, группы идут подряд.

**Правка секции md — обновить body и annotation:**

```json
[{"id": 1, "action": "read_unit",
  "arguments": {"file_path": "docs/CONFIG.md",
                "address": {"section_number": "3"},
                "part": "head,annotation"}}]

[{"id": 2, "action": "replace_unit",
  "arguments": {"file_path": "docs/CONFIG.md",
                "address": {"section_number": "3"},
                "part": "body",
                "new_text": "Новое тело секции.\n\n### 3.1 Подсекция\n\nтело подсекции"}}]

[{"id": 3, "action": "set_annotation",
  "arguments": {"file_path": "docs/CONFIG.md",
                "address": {"section_number": "3"},
                "text": "Обновлённое описание секции"}}]
```

Порядок важен: действия выполняются по порядку. `replace_unit part="body"` сохраняет `head` и `annotation` — заголовок и summary не потеряются.

**Правка функции Python — заменить тело, сохранив сигнатуру:**

```json
[{"id": "read", "action": "read_unit",
  "arguments": {"file_path": "toolkit/core/patcher.py",
                "address": {"qualname": "Patcher._apply_one"},
                "part": "head,annotation"}}]

[{"id": "body", "action": "replace_unit",
  "arguments": {"file_path": "toolkit/core/patcher.py",
                "address": {"qualname": "Patcher._apply_one"},
                "part": "body",
                "new_text": "return self._dispatch(patch)"}}]
```

**Заменить один блок (statement) в большом теле:**

```json
[{"id": "read", "action": "read_unit",
  "arguments": {"file_path": "toolkit/core/patcher.py",
                "address": {"qualname": "Patcher._apply_one"},
                "block": "1-5"}}]

[{"id": "repl", "action": "replace_unit",
  "arguments": {"file_path": "toolkit/core/patcher.py",
                "address": {"qualname": "Patcher._apply_one"},
                "block": 3,
                "new_text": "return self._short_circuit(patch)"}}]
```

`block=3` — третий top-level statement. Если правок несколько — заменяй диапазон (`block="3-5"`) или **всё тело** через `replace_unit part="body"` (один вызов вместо нескольких `replace_unit(block=...)` с пересчётом номеров после каждой правки).

**Вставить блок в начало / конец / рядом с anchor:**

```json
[{"id": "ins", "action": "insert_block",
  "arguments": {"file_path": "toolkit/core/patcher.py",
                "address": {"qualname": "Patcher._apply_one"},
                "new_text": "self._trace(patch)",
                "position": "before",
                "anchor": 1}}]
```

`anchor` — номер блока или qualname дочернего unit'а (для класса — метод). Для `start` / `end` anchor не нужен.

**Удалить блок:**

```json
[{"id": "del", "action": "replace_unit",
  "arguments": {"file_path": "toolkit/core/patcher.py",
                "address": {"qualname": "Patcher._legacy_log"},
                "block": 2,
                "new_text": ""}}]
```

Пустой `new_text` вместе с `block` — удаление этих блоков. Пустой `new_text` вместе с `part="all"` — удаление unit'а целиком.

**Проследить цепочку вызовов символа:**

```json
[{"id": "read", "action": "read_unit",
  "arguments": {"file_path": "toolkit/core/patcher.py",
                "address": {"qualname": "Patcher._apply_one"},
                "part": "head,annotation"}}]

[{"id": "trace", "action": "symbol_graph",
  "arguments": {"qualname": "Patcher._apply_one", "depth": 2}}]
```

`read_unit` показывает сигнатуру; `symbol_graph` — кого оно зовёт на два шага вниз и кто зовёт его, с line-адресами. Вместо серии `read_unit → find_symbol → read_unit` на каждого соседа — один `symbol_graph`. Если в цепочке нашлось интересное — `read_unit` уже точечно по этому символу.

**Скопировать функцию в другой файл:**

```json
[{"id": "copy", "action": "copy_unit",
  "arguments": {"source_file": "toolkit/utils.py",
                "target_file": "toolkit/config.py",
                "selector": {"qualname": "parse_config"},
                "position": "end"}}]

[{"id": "rebuild", "action": "rebuild_code_index", "arguments": {}}]
```

`copy_unit` копирует unit целиком (с телом и annotation) и **не трогает** source. Транзитивные зависимости (импорты, `common.X`) **не переносятся** — добавляй отдельным `replace_unit` / `insert_block`.

**Создать файл и пересобрать доки:**

```json
[{"id": 1, "action": "create_file",
  "arguments": {"file_path": "docs/NEW.md",
                "file_content": "# NEW\n\n## 1. Раздел\n<!-- summary: ... -->\n\nтело\n"}}]

[{"id": 2, "action": "rebuild_index", "arguments": {}}]
```

В выводе увидишь `+ docs/NEW.md  (N стр., M KB, mtime ...)` и версию `[vN]` — это и есть подтверждение, что индекс догнал реальность.
